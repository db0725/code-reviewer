# 候选问题复核：从原文证据到反证检查

## 目标

文件、行号和原文存在，只能证明模型引用了真实代码。要判断缺陷，还需要检查调用副作用、旧版行为、接口契约及错误影响。

新版把流程拆成“发现候选 → 独立上下文复核 → 分类展示”。这里的独立指复核不继承发现阶段的完整对话，不代表使用了独立训练的模型，也不代表取得了形式化证明。

## 一次复核如何执行

1. 保留原候选，不让复核模型悄悄把它改成另一个主张。
2. 从固定内存快照提取候选位置及引用原文。
3. 用 Python AST 查找所在函数、同包附近的同名被调用函数、装饰器、旧版所在函数和旧版调用目标；必要时补充调用方线索。
4. 生成有大小限制的 before/after 证据包。完整函数过长时只展示头尾并标记缺口，不冒充完整覆盖。
5. 新建模型上下文，通过严格 `verify_candidate` 函数提交结论。
6. 本机验证候选编号、结论结构、原文位置和证据是否完整出现在本次证据包中。
7. 展示支持、反驳、待核实三类结果，保留原候选与反证。

这一步不会运行被审查项目、下载模型或读取数据集。索引只提供按名称与包路径匹配的静态线索，不能保证动态分派、别名、继承和运行时注入都能解析。

## 为什么要取回函数尾部和旧版调用

状态更新、资源释放等副作用可能位于函数后半段。如果只读函数前80行，就可能错过实际执行的清理或标志更新。

另一类问题是“新版删除了调用”。只分析新版的调用列表，无法取回已经消失的旧调用及其副作用。因此证据包还会检查旧版函数与其调用目标，帮助判断问题是否由本次修改引入。

同名定义优先选择与候选路径有共同包前缀的实现，降低旧服务、兼容入口等无关同名函数占用证据预算的风险；这仍是启发式匹配，不是完整符号解析。

## 三个必须分别判断的问题

| 字段 | 判断内容 |
| --- | --- |
| `mechanism_assessment` | 原候选描述的故障因果链是否成立 |
| `regression_assessment` | 是否由本次修改引入，而非旧版本已有行为 |
| `impact_assessment` | 是否有具体错误结果，而不只是字段、格式或表示不同 |

每项为 `supported`、`contradicted` 或 `unknown`。

- 整体 `supported`：三项都要得到支持，并引用支持证据。含义是“模型静态复核支持”，仍需开发者验收。
- 整体 `refuted`：至少一个关键判断被代码反驳，并引用反证。原候选保留在复核区，不继续作为支持的问题展示。
- 整体 `uncertain`：缺少关键契约、动态行为无法判断、输出不合法、接口失败或预算不足时保留待核实。

主机只能检查这些声明之间的结构一致性及引用真实性，不能自动证明模型的语义判断正确。不同展示字段和内部比较状态不相等，也不必然意味着缺陷。

## 与原任务共享预算

默认仍是最多50次调用、300秒审查时间、600,000累计输入预算预检。

主机会从发现阶段预留最多6次调用、75秒和120,000输入预检额度供复核使用；实际复核最多处理3个候选，每个最多2次尝试。高严重级候选优先。发现和复核的实际调用、时间及已返回用量最后合并，不能把它们当成两份独立的50次预算。

超出处理数量或预算的候选不会丢弃，会显示为待核实。存在待核实候选时，总任务不显示成“完成且没有问题”。供应商没有返回的消耗标记未知。

为明确对照，命令行仍支持：

```powershell
.\.venv\Scripts\python.exe review_git.py --repo "仓库路径" --base "旧提交" --head "新提交" --verification off --output tests/results/discovery-only-new-run
```

默认不需要这个开关，正常仓库审查会执行复核。原版 `--engine legacy` 仅用于显式对照，不接入新复核阶段。

## 复核已保存候选

不用再次审查整个仓库：

```powershell
.\.venv\Scripts\python.exe -m tests.verify_saved_candidate --repo "仓库路径" --report "已保存的report.json" --candidate-index 1 --output tests/results/new-candidate-review
```

脚本从记录中的提交编号加载固定快照，最多2次请求、75秒，保存结构化结论、实际证据包和Markdown报告，禁止覆盖已有目录。
