| --- | ---: | ---: | --- |
| 完成任务 | 11/12 | 12/12 | 本次复测没有因格式问题中断 |
| 结构/JSON 校验反馈 | 18 次 | 0 次 | 本次输出结构稳定性改善 |

## 2. 实际发生的实现错误与修复

### E01：把 unified diff 的上下文范围写错在测试里

**现象**：第一轮自动测试中，`test_diff_line_mapping` 失败。我断言 diff 应包含 `@@ -1,6 +1,6 @@`，实际生成的是 `@@ -3,4 +3,4 @@`。

**原因与责任**：我把完整文件的范围误当成默认三行上下文的 diff hunk 范围。这里首先是测试预期错误，不是已经证明 diff 生成算法出错。

**解决办法**：根据真实变更位置和 `difflib.unified_diff(..., n=3)` 的行为修正断言；同时保留独立的新旧行号映射测试，检查新增、删除和上下文行。

**前后效果**：原断言稳定失败，修正后通过；当前没有据此宣称“修复了所有 diff 行号问题”。

证据：开发早期测试输出，以及 [test_review.py](../tests/test_review.py) 中的 `test_diff_line_mapping`、[examples.py](../examples.py)。

### E02：固定回放没有先通过自身完整验收

**现象**：第一版回放中，折扣示例和正常重构完成，用户查询示例 `accounts` 失败；`test_all_replays_and_reports` 也失败。

**原因与责任**：我没有先确保固定回放数据与当前校验要求完全一致。历史记录能确认该回放失败、修复涉及 `replay.py`，以及随后三组回放通过；但旧版失败记录没有完整保留具体错误字段，不能把“某一个引用行号写错”作为已经独立证明的根因。回放同样必须经过证据校验，不能因为答案是预设的就跳过验证。

**解决办法**：重新对照示例的修改后代码，校准问题与关联引用；当前 `accounts.py` 问题定位为第 6 行，关联 `repository.py` 的返回语句在第 12 行。保留所有回放与报告的回归检查。

**前后效果**：回放由 **2/3 完成变为 3/3 完成**。这只证明预设脚本和展示流程可运行，不代表模型能力。

证据：[replay.py](../replay.py)、回放结果（本机原始材料：`tests/results/evaluation-results.json`）、开发早期回放与单元测试记录。

### E03：没有把浏览器断开 SSE 当作正常情况完整处理

**现象**：早期浏览器检查后，服务端在 `stream_events()` 写入数据时出现 `ConnectionAbortedError: [WinError 10053]` 的堆栈。

**原因与责任**：刷新页面、关闭页面会断开长连接。我最初没有完整覆盖 Windows 上的连接中止异常，正常离开页面也会污染服务日志。

**解决办法**：在 SSE 写入流程中将连接中止等客户端断开情况按正常断连结束；补充模拟浏览器断开的回归测试。

**前后效果**：修复前实际出现异常堆栈；修复后 `test_sse_client_abort_is_normal_disconnect` 通过，刷新恢复与事件续传检查通过。没有把它包装成“服务从此不会断连”。

证据：[server.py](../server.py)、[test_review.py](../tests/test_review.py)。

### E04：最初给模型的格式和证据纠错信息不够具体

**现象**：首次真实 DeepSeek 内置示例验收，用户查询示例连续三次校验失败：第 1、3 次输出不符合完整 JSON 对象要求，第 2 次代码证据与目标行不匹配，任务停止。

**原因与责任**：初版协议主要靠提示词和 JSON Mode；证据出错时，反馈只有“与目标行不匹配”，没有帮助模型确认实际行号与原文。对于未查看的关联代码，约束也不够明确。

**解决办法**：要求查阅未展示的关联代码后再引用；明确 JSON 转义要求；错误反馈给出目标文件、行号和目标行原文，提示使用 `read_file` 更正；非思考模式温度设为 0.2。没有放宽证据匹配标准，也没有增加失败重试上限。

**前后效果**：

| 内置示例 | 首轮 JSON Mode | 改进后 JSON Mode |
| --- | --- | --- |
| 折扣计算 | 完成，4 轮、5.30 秒 | 完成，3 轮、15.86 秒 |
| 用户查询 | 失败，3 轮、16.50 秒，3 次校验反馈 | 完成，3 轮、3.75 秒，无校验反馈 |
| 正常重构 | 完成，4 轮、15.44 秒 | 完成，3 轮、14.42 秒 |

这说明用户查询案例得到修复，但不能说所有示例都更快；折扣案例该次反而更慢。这是早于后续 Structured Outputs 改造的另一阶段实验。

证据：首次真实结果（本机原始材料：`tests/results/evaluation-real-initial.json`）、改进后真实结果（本机原始材料：`tests/results/evaluation-real.json`）。

### E05：把主要稳定性希望放在 JSON Mode 和提示词上

**现象**：DKNet 首轮 20 案例的 Agent 审查中，出现 27 次输出校验反馈；DK001 因连续格式错误未完成。对应 12 个开发案例中，有 18 次结构反馈，完成 11/12。

**原因与责任**：JSON Mode 没有充分表达“每轮一个动作、动作对应特定参数、最终报告字段固定”的业务结构。我保留了严格拒绝机制，但最初生成协议约束不足，导致模型输出多个动作或额外内容后再被动纠错。

**解决办法**：用 Pydantic 定义动作与报告，以 `action` 区分分支，严格限制字段类型和额外字段；从同一模型生成服务端兼容 JSON Schema。最终采用 Beta 严格函数调用，而不是只继续堆提示词。

**前后效果**：相同开发集的结构反馈 **18 → 0**，完成 **11/12 → 12/12**。这是结构约束、Pydantic、传输包装和历史配对的组合结果，不能全部归功于 Pydantic。

证据：[schemas.py](../schemas.py)、[review.py](../review.py)、[对比报告](../tests/BENCHMARK_STRUCTURED_RESULTS.md)。

### E06：声明了 JSON Schema，却遗漏显式 `strict=true`

**现象**：第一次 Responses 结构化开发集实验仍有 17 次结构反馈，Agent 完成 10/12；比原 JSON Mode 的完成数量还少。

**原因与责任**：我在请求中声明了 `json_schema`，却没有显式开启严格模式。单次兼容性探针能得到合规内容，不等于多轮场景已经可靠受约束。

**解决办法**：补上 `strict=true`，检查真正发出的请求载荷，并增加接口适配测试。随后继续处理严格模式暴露出的 Schema 兼容问题。

**前后效果**：开启 strict 后的 Responses 试验为 **10/12 完成、16 次结构反馈**。因此“补 strict”并没有单独解决问题；最终必须更换传输通道并修正多轮历史。

证据：未显式 strict 的试验（独立基准文件：`../review-agent-bench/results/structured-dev/report.json`）、显式 strict 的试验（独立基准文件：`../review-agent-bench/results/structured-strict-dev/report.json`）。

### E07：Schema 转换时误删业务字段 `title`

**现象**：把 Pydantic Schema 转成服务端兼容子集时，转换函数曾将问题报告中的 `title` 字段一起删除。

**原因与责任**：我把 Schema 元数据的 `title` 和 `properties` 内名为 `title` 的业务属性当成一回事，递归时对所有同名键都应用了过滤规则。这是我写的转换代码错误。

**解决办法**：专门处理 `properties`：属性名原样保留，只转换属性对应的 Schema 内容。增加检查，确保问题模型的 `title` 同时出现在 `properties` 与 `required` 中。

**前后效果**：远端结构与本地模型之间的字段遗漏被消除，回归测试通过。没有单独针对这个修改跑一组模型消融，因此没有独立的准确率提升数字。

证据：[schemas.py](../schemas.py) 的 `provider_schema`、[test_schemas.py](../tests/test_schemas.py) 的 `test_schema_keeps_title_property_and_has_no_external_refs`。

### E08：没有预先验证空参数对象的服务端兼容性

**现象**：开启严格模式后，接口拒绝 `get_diff` 所使用的空属性对象，返回 HTTP 400；诊断信息为 `An object with no properties is not allowed.`。

**原因与责任**：本地合法的 Pydantic/JSON Schema，不一定属于服务端支持的子集。我没有在批量运行前覆盖这个兼容边界。

**解决办法**：传输层将 `get_diff` 改为 `{"step":{"action":"get_diff"}}`，省略无用途的空 `arguments`；本地解析后恢复 `arguments={}`。其他工具和只读执行逻辑保持原接口。增加所有对象必须包含属性的 Schema 检查。

**前后效果**：该 Schema 拒绝原因被消除，后续真实动作探针可通过。不能据此宣称其他上游 HTTP 错误也被解决。

证据：[schemas.py](../schemas.py) 的 `WireGetDiffAction`、`wire_action`、`validate_action_json`，以及 Schema 回归检查。

### E09：依据接口名称推断通道足够稳定，真实上下文验证不足

**现象**：Responses 显式 strict 的多轮试验仍出现非 JSON 文本，诊断请求直接返回 DSML 原生工具调用标记，例如 `<…DSML… calls>`。Agent 仅完成 10/12。

**原因与责任**：我最初认为 Responses 的 JSON Schema 配置可以直接承担这套显式动作循环。实际观测表明，在当时的模型、请求参数和代码上下文组合下，响应没有始终遵守约定。不能据此断言所有 Responses 请求或服务商实现都有相同缺陷。

**尝试过但无效的办法**：增加 `tool_choice=none`、禁止 DSML 的提示，以及简化工具说明后，诊断请求仍返回了相同类别的标记。这些尝试没有被写成成功修复。

**最终办法**：默认改用 `/beta/chat/completions` 的官方严格函数调用，强制通过唯一的 `review_step` 函数传输 JSON 参数；Responses 保留为显式实验选项，不自动降级，也不解析 DSML 来冒充合规 JSON。

**前后效果**：Responses 阶段 **10/12 完成、16 次结构反馈**；首次严格函数调用阶段 **12/12 完成、17 次结构反馈**；配合后续历史配对修复，最终 **12/12 完成、0 次结构反馈**。

证据：[review.py](../review.py) 三种显式协议，以及三个独立实验目录中的 `report.json`。

### E10：单轮探针的代表性太弱，导致过早进入完整批量试验

**现象**：复制指定动作的六项探针曾全部通过，但真实多轮代码审查仍失败。

**原因与责任**：探针只验证短输入下的单次返回，不包含真实 diff、工具结果、消息历史和纠错。我对“能按格式抄一个动作”和“Agent 能多轮稳定调查”的差异考虑不够，额外花费了接口调用。

**解决办法**：将单次格式探针、原生消息配对测试、失败案例诊断、完整开发组复测分开；每一层报告自己的验证范围，中间失败结果保留。

**前后效果**：最后既有 **6/6 单次探针**，也有 **24/24 多轮任务完成**的记录，而不是只拿探针结果交付。没有反复运行独立保留组来挑选最好结果。

证据：[probe_structured.py](../tests/probe_structured.py)、最终探针（本机原始材料：`tests/results/structured-probe-final.json`）、最终多轮结果（独立基准文件：`../review-agent-bench/results/strict-native-dev/report.json`）。

### E11：强制一个函数名称，不等于一轮只有一次函数调用

**现象**：严格函数调用诊断中，模型一次返回两个 `review_step`：一个取 diff，一个请求读取文件。每个参数单独合法，也不符合“一轮一个动作”。

**原因与责任**：`tool_choice` 约束名称，并不自动等价于约束返回数量。初始诊断只查看第一个调用，不能直接照搬为正式执行逻辑。

**解决办法**：明确要求每轮一次调用，并在适配层检查：只有一个调用、名称正确、参数为 JSON 文本、没有额外普通文本。多调用整轮拒绝，反馈纠正，不能偷偷只执行第一个。

**前后效果**：模拟多调用、附加文本、未知函数和空调用的测试均被拒绝；可恢复场景在第二轮完成，拒绝的动作没有被执行。最后开发组未出现这类反馈，但不保证以后不会出现。

证据：[test_strict_tools.py](../tests/test_strict_tools.py)。

### E12：异常继承关系处理错了，把可纠正错误变成终止错误

**现象**：新增严格调用测试时，4 个子场景抛出的异常类型不符合预期，另有一项恢复测试断言失败。本应反馈后纠正的任务直接失败。

**原因与责任**：`SchemaFormatError` 继承自 `FormatError`，后者继承 `ValueError`。我在适配层末尾使用通用 `except (..., ValueError, ...)`，把主动抛出的格式错误也捕获并改成 `ModelError`，循环无法进入格式纠正分支。

**解决办法**：在通用异常分支之前单独 `except SchemaFormatError: raise`；在 Agent 循环中专门反馈这种错误，并继续使用原有连续三次错误与 12 轮预算。

**前后效果**：严格调用模块当时的 6 项测试全部通过；之后补充原生历史配对测试，该模块当前为 7 项。没有把上游拒绝、截断或网络故障错误地改成可无限重试。

证据：[review.py](../review.py) 的异常分支与 `format_feedback`，以及 [test_strict_tools.py](../tests/test_strict_tools.py)。

### E13：换了原生函数调用，却继续用普通文本拼接多轮历史

**现象**：首次 Beta 严格函数调用复测虽然全部完成，Agent 仍有 17 次结构反馈、94 次模型调用，输入量达到 523,129 token。

**原因与责任**：模型通过原生函数调用提交动作，但我仍把动作改写成普通 assistant JSON，把工具结果当普通 user 文本回填，没有正确延续原生调用 ID 与工具结果之间的关系。这是迁移传输协议时没有同步修改历史格式。

**解决办法**：保存实际调用的 ID 和函数信息；在构造下一轮历史时恢复 assistant 的 `tool_calls`，将观察结果或校验失败反馈放入与其 ID 配对的 `role=tool` 消息。被整轮拒绝的多调用不伪造执行结果。

**前后效果，均为 12 个开发案例的 Agent**：

| 指标 | 严格函数调用，普通文本历史 | 最终原生历史配对 |
| --- | ---: | ---: |
| 完成任务 | 12/12 | 12/12 |
| 结构反馈 | 17 | 0 |
| 模型调用 | 94 | 70 |
| 输入 token | 523,129 | 364,273 |
| 输出 token | 10,928 | 6,909 |
| 平均耗时 | 18.82 秒 | 17.95 秒 |

这是两次整组实验的观察，不是严格的单因素因果证明；模型输出存在波动。但同时有专门的消息配对回归测试，证明最终请求实际保留了原调用 ID 和工具结果。

证据：普通历史实验（独立基准文件：`../review-agent-bench/results/strict-function-dev/report.json`）、配对后实验（独立基准文件：`../review-agent-bench/results/strict-native-dev/report.json`）、[review.py](../review.py) 的 `_function_history`、原生历史测试。

### E14：探针输入没有按真实传输包装，混淆了“格式合法”和“动作符合要求”

**现象**：首次严格函数探针中，四项符合预期，搜索和查定义两项不符合期望。它们没有产生 Pydantic 解析异常，而是返回动作与要求不一致。

**原因与责任**：探针给模型的指定动作仍是旧版扁平对象，没有完整体现 `{"step": ...}` 的新传输格式；又只用一个通过/失败标志，没有分开表示结构校验与动作一致性。这不能被简单计为“两次 JSON 格式错误”。

**解决办法**：探针输入也使用完整包装，明确通过 `review_step` 提交要求的动作；记录 `structure_valid`、`requested_action`、`returned_action`。新增输出文件参数与拒绝覆盖检查，保留早期记录。

**前后效果**：指定动作一致性从 **4/6 → 6/6**；最后六项均能解析、动作也符合要求。没有因此宣称模型在所有用户指令下都能正确选择工具。

证据：早期函数探针（本机原始材料：`tests/results/structured-probe.json`）、最终探针（本机原始材料：`tests/results/structured-probe-final.json`）、[probe_structured.py](../tests/probe_structured.py)。

### E15：依赖变化后，旧的“零依赖”说明和系统 Python 命令没有立即同步

**现象**：初版用标准库，说明写着“无需安装依赖”；加入 Pydantic 后，这些表述在开发中间阶段仍暂时存在。若按旧命令使用没有 Pydantic 的系统 Python，不能运行新实现。

**原因与责任**：实现与交付说明的更新不同步。引入 Pydantic 是本次认可的技术调整，但必须相应维护启动路径和依赖说明。

**解决办法**：建立项目 `.venv`，锁定兼容 Python 3.9 的依赖；增加 `setup.ps1`，启动脚本使用项目解释器；Demo 和测试集 README 更新命令，网页页脚移除“零依赖”。

**前后效果**：在 Python 3.9.7 的项目环境中安装成功，76 项自动测试通过；实际由 `start.ps1 -Port 8767` 启动后发起真实审查，5 轮、6.61 秒完成并下载 Markdown。最终启动使用 UTF-8 模式，减少中文终端输出乱码。

证据：[requirements.txt](../requirements.txt)、[setup.ps1](../setup.ps1)、[start.ps1](../start.ps1)、两个目录的 README。

## 3. 评估设计上的错误与尚未解决的问题

### E16：DK003 的标签把函数契约变化直接当成业务功能缺陷

**现象**：我构造了交换坐标返回顺序的改动，并将独立函数验收失败标成有缺陷。模型查阅调用者后指出：CSV 校验流程只验证“能不能解析”，没有消费返回坐标的顺序。

**原因与责任**：验收覆盖的是返回值契约，我在案例命名和缺陷标签中没有充分区分函数变化与实际调用链中的可观察影响。

**已采取的处理**：不修改已经冻结的案例来抬高分数；在首次分析和后续对比中明确这个边界，不把“不报告 DK003”直接解释成漏掉一个已证明的业务 Bug。

**当前效果**：统计解释得到纠正，**案例本身尚未重做**。下一版应把它归为契约变化，或改在实际消费坐标的路径中建立端到端验收。

证据：catalog.py（独立基准文件：`../review-agent-bench/catalog.py`） 的 DK003、[首次结果分析](../tests/BENCHMARK_INITIAL_RESULTS.md)。

### E17：DK011 缺少浮点坐标精度的明确业务容忍约定

**现象**：把浮点转换成整数会确定地损失小数；但模型可能以不到一个像素为由不报告。当前没有独立业务规则证明这种误差一定允许或一定不可接受。

**原因与责任**：我写出了函数级验收，却没有补全业务容忍范围。因此“预设数值改变”与“应报告的功能缺陷”之间仍有缺口。

**已采取的处理**：保留标签边界说明，不凭模型态度判定可接受，也不推断医学效果。

**当前效果**：评估表述已收敛，**业务契约仍待明确**。不能写成这项问题已经被完全修复。

证据：catalog.py（独立基准文件：`../review-agent-bench/catalog.py`） 的 DK011、[RESULTS.md](../tests/BENCHMARK_INITIAL_RESULTS.md)。

### E18：报告定位正确，但解释仍可能错误，现有自动验证不能发现

**现象**：首轮 DK013 的报告指出了路径参数反转，但对绝对路径拼接的解释不准确。对于 `os.path.join(relative, absolute_root)`，后面的绝对路径会使前面的相对部分失效，不能简单理解成拼在一起。

**原因与责任**：模型生成了错误解释，而我实现的验证主要检查文件、行号和代码原文，没有验证每条因果解释。问题成立与解释正确是两个维度。

**已采取的处理**：人工复核结果中指出错误，不把位置命中当语义正确；报告继续明确“代码位置与证据匹配，缺陷语义尚需人工复核”。

**当前效果**：这个误判已被记录，但**自动语义验证尚未实现**，不能说当前系统已经能自动纠正这类解释。

证据：[首次报告分析](../tests/BENCHMARK_INITIAL_RESULTS.md)、DK013 原始任务记录（独立基准文件：`../review-agent-bench/results/initial/report.json`）。

### E19：上下文管理过于粗放，整文件反复进入历史

**现象**：首轮全量实验，Agent 输入 337,077 token，diff 基线输入 11,084 token，相差约 30.41 倍。最终结构化版本相比原开发组，输入量也没有下降。

**原因与责任**：`read_file` 目前返回整文件，每轮请求又带上完整历史；已读内容可能重复进入上下文。增加格式约束和修复失败任务，也不自动等于节约 token。

**已经改善的部分**：原生历史配对使输入量相对“严格函数调用但历史不正确”的中间版从 523,129 降到 364,273 token。

**尚未解决的部分**：相对原开发组仍增加约 64.15%。按行段或函数读取、上下文去重、缓存与输入预算尚未实现。不要把本次工作写成“显著降低成本”，也不能在没有价格与缓存计费依据时用 token 比直接推算金额。

证据：[首轮结果](../tests/BENCHMARK_INITIAL_RESULTS.md)、[结构化对比](../tests/BENCHMARK_STRUCTURED_RESULTS.md)、[CodeTools](../review.py)。

### E20：优化后的泛化验证仍缺少新的独立保留集

**现象**：第一轮已经观察过 DK013～DK020 的结果，这 8 个案例此后不能继续称为“未见测试集”。结构化改造只复测了开发组。

**原因与责任**：现有小样本集同时承载开发、初始对照和效果观察，没有另建新保留集支撑后续泛化结论。第一轮运行保留组本身是预定评估，并不等于数据泄漏事故；问题在于不能继续复用“未见”的名义。

**已采取的处理**：调参后只运行开发组；比较脚本拒绝将保留组作为本次协议改进的对比来源；保留所有实验，不替换失败任务。

**当前效果**：比较口径得到控制，**新的独立保留集尚未建立**。当前只能支持开发集上的工程稳定性结论，不能证明任意仓库上的审查能力。

证据：freeze.json（独立基准文件：`../review-agent-bench/freeze.json`）、compare_protocols.py（独立基准文件：`../review-agent-bench/compare_protocols.py`）、test_comparison.py（独立基准文件：`../review-agent-bench/test_comparison.py`）。

## 4. 开发与验证操作中的失误

这些问题影响了开发效率或验证过程，不应被包装成产品功能缺陷。相同类型的重复失误合并记录。

| 编号 | 实际发生的问题 | 原因与处理 | 修复后的效果与边界 |
| --- | --- | --- | --- |
| O01 | 早期本机 HTTP 测试出现 WinError 10013/URLError | 环境限制阻止套接字访问；同时应排除系统代理对本机地址的干扰。本机测试使用无代理访问，并在允许本机通信的执行环境重跑 | HTTP、SSE 和模拟上游测试通过；不是修改了审查算法来解决 |

| O04 | 从根目录读取 `requirements.txt`，以及从测试集目录读取 Demo 的 `replay.py`、`examples.py` | 我在多个子目录之间切换时使用了错误的相对路径；此类读取错误在整理复盘时也重复发生 | 指定正确工作目录或完整路径后读取成功；属于可避免的操作失误，没有改动或丢失原文件 |
| O05 | 在 Demo 目录查找只存在于测试集目录的 `STRUCTURED_RESULTS.md` | 同样是目录归属判断错误；忽略错误输出也不能证明文件存在 | 后续以真实路径链接并检查；不把文件不存在归为生成报告失败 |

| O08 | 中文控制台输出曾出现乱码 | Python、终端和捕获输出编码不一致 | 最终启动明确使用 `-X utf8`；新命令与文档也统一使用 UTF-8。不是浏览器网页编码故障 |

## 7. 面试和项目记录可以怎样使用这份材料

最适合展开的是三条完整经历：

1. **输出稳定性**：从 JSON Mode 的多动作与额外内容失败，经过 Schema、strict 兼容和传输通道验证，最终落到严格函数调用与 Pydantic 双层检查。重点讲实际请求和多轮验证，不能只说“用了 Pydantic 所以模型不会乱输出”。
2. **协议迁移问题**：函数调用迁移后，历史仍按普通文本回传，导致重复纠错；保留真实调用 ID 并配对工具结果后，本轮反馈从 17 次降到 0 次。可以展示请求结构与对应回归测试。
3. **评估可信度**：构造案例后发现，函数测试失败未必影响当前业务路径；将位置命中、语义正确、完成率和成本分别统计，保留失败与有争议标签，避免只展示好看的数字。

可以使用的事实表述：

> 为 Python 代码审查 Agent 实现严格函数调用与 Pydantic 校验，处理多动作返回、Schema 子集兼容、异常分类和多轮工具结果配对；在固定的 12 个 DKNet 开发案例中，Agent 输出结构校验反馈由 18 次降至本轮 0 次，完成任务由 11 个增至 12 个，并保留调用量、耗时及全部失败实验。

不应使用的表述包括“通用准确率 100%”“零幻觉”“完全消除格式错误”“成本降低 64%”“自动证明所有缺陷”。实际数据并不支持这些说法。

## 后续工程复盘补充（2026-11-02）

### 大仓库 token 大幅累积且无法交付

旧版FunASR记录为50次调用、11,344,663输入token，最终未完成。原因包括重复获取已有diff、全文读取，以及每轮回填不断增长的完整历史。改造为紧凑变更分批、按行读取、BM25/AST检索、已展示证据台账与批次收尾。最终开发复测为25次调用、192,774输入token，8/8批代码范围交付。评审范围变为28个代码文件、16个文本变更仅作上下文，因此不能写成同覆盖准确率提高。

### 第一轮节省token之后仍然超时

首次分批试验只记录到164,071输入token，却在300秒停止，仅交付8/14批。原因是串行请求实际约10–14秒，分批太细会增加调用延迟。随后用紧凑diff减少批次数，并按已观测请求耗时分配余下调用机会；第二轮8/8批交付，用时294.67秒。没有增加300秒上限，也没有隐藏前一次失败。当前只验证一次完成，不能保证长期稳定，更不能宣称整体提速。

### 有原文证据的报告仍可能误判调用链

最终FunASR模型提出1条候选，声称首包标志未更新。代码助手静态查看被调用的sending函数，发现它在105–108行更新该标志；原报告关键推断不成立，未计入确认缺陷。当前解决方式是保留原始报告并单独记录反证，没有自动完成语义验证。后续仍需候选复核与独立验收。

详细用量、范围、失败记录和复核边界见[分批引擎开发复测](../tests/CONTEXT_ENGINE_RESULTS.md)。


## 候选复核与新增评测补充（2026-11-03）

### 只分析新版调用，遗漏已经删除的旧调用副作用

开发组初轮有一个真实缺陷只能得到不确定结论：新版已删掉send调用，但证据包没有旧send实现，无法证明状态更新由本次修改丢失。补充旧版所在函数和旧版被调用函数，并保留公开契约背景。开发结果和首轮不确定记录都保留，没有修改冻结案例来提高分数。

### 复核找到反证，仍把局部事实当作整体支持

历史FunASR候选的首轮自动复核已经看到发送函数更新首包标志，却仍因局部字段不同而支持原候选。改为分别判断机制、变更引入性与影响，要求支持时三项全部支持，不能偷偷改写原候选。进一步优先同包定义，减少无关同名实现占据上下文。复测结果为待核实，不再作为支持问题发布；没有宣称已自动证明原候选错误。

### 严格结构化输出不等于满足全部本地约束

开发试验出现支持证据数组过长；保留组局部证据条件中两次结论的整体支持与必要判断不一致，也被主机拒绝。保留失败并分别统计，不把它们记成无问题或从评测分母删除。生产复核提供最多两次有限纠错；给定候选对照固定一次请求，避免按重试结果挑最好成绩。

新增12个合成案例中4个用于开发，8个保留组在真实观察前冻结。增强证据复核8/8匹配预期；局部条件2/8判别、4不确定、2被拒绝。端到端4个预置缺陷报告与验收匹配、4个正常改动无告警，但没有据此宣称通用准确率或证明降低真实仓库误报率。

详情见[候选复核和新增评测结果](../tests/VERIFICATION_RESULTS.md)。

## 前端改版补充（2026-11-11）

### 只看文字色，没有检查增删背景上的对比度

改版初稿的代码行号在白底上可读，但在新增和删除背景上只有约4.14–4.15:1。浏览器计算样式检查发现后，加深行号颜色，复查相关场景通过4.5:1门槛。对比度必须检查实际前景与背景组合，不能仅凭色板推断。

### 新增失败提示，没有同步重置初始空状态

增加启动失败与等待文案后，最初的重置函数只恢复空状态可见性，没有清除旧内容，导致切换输入后仍显示此前失败或启动文案。实际截图审阅发现后，在统一重置入口恢复标题与说明，并增加Node和浏览器断言。切换示例与仓库预览后已正确恢复“尚未开始审查”。

本轮9项Node状态检查与独立Chrome渲染、交互检查通过，真实模型调用为0。详情见[界面改版与验证记录](../tests/UI_REDESIGN_RESULTS.md)。

### 收紧了装饰，却没有把代码阅读空间交给用户

第一轮固定三栏布局仍让本地仓库的说明和版本信息占用编辑器上部，也没有面板拖动能力。用户截图指出代码窗口依然偏小，说明仅改善视觉密度没有解决阅读任务。补充默认收起仓库说明、两侧宽度与整体高度拖动、面板隐藏、专注与恢复、本机布局记忆。同一1440×900的DKNet预览中，说明收起使代码容器从约340px增至544px高；专注后宽度从722px增至1406px。通过实际拖动、键盘、刷新和手机专注检查，不再只凭静态截图判断可用。
