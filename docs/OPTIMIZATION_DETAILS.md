# 新版本优化说明：改了什么，为什么指标会变化

日期：2026-11-02。本文解释 Code Review Agent 从完整历史循环到 `bounded-batches-v2.1` 的改造。数字来自已保存的真实运行记录，本次编写文档没有重新调用模型。

## 1. 先明确：哪些指标改善了

这轮主要改善了**累计输入量、有限预算内的任务交付，以及本地仓库预览速度**。没有证明通用缺陷识别准确率提高，也没有证明模型审查阶段变快。

固定的 FunASR 代码版本是：

- 修改前：`2534a97d305b6706820900ea00706450307c813f`。
- 修改后：`7710a59c205746210474ae176bb0d2034b1e8081`。
- 本地白名单快照：174 个文件，1,186,485 字节；白名单变更 44 个文件。

| 指标 | 历史完整历史版本 | 最终新版本 | 如何理解 |
| --- | --- | --- | --- |
| 累计输入 token | 11,344,663 | 192,774 | 记录值减少约 98.30% |
| 模型调用 | 50 次 | 25 次 | 调用次数减少 50% |
| 模型审查阶段 | 289.23 秒 | 294.67 秒 | 没有提速，反而略有增加 |
| 网页预览 | 30.14 秒 | 2.56 秒 | 本次记录中耗时减少约 91.51% |
| 最终交付 | 达到次数上限，未完成 | 8/8 批代码范围交付 | 新版在既定范围内提交了报告 |
| 输出 token | 3,441 | 4,189 | 没有下降；输出量不是本次优化目标 |

输入下降比例的计算为：

```text
(11,344,663 - 192,774) / 11,344,663 × 100% ≈ 98.30%
```

**比较存在范围变化。** 新版把 28 个 Python/Shell 变更文件纳入代码审查，另外 16 个文档、说明与配置文本只作为契约上下文，不单独评审。旧版初始输入包含全部 44 个白名单文件的 diff。不能把上述结果表述成“相同评审范围、相同准确率下省了98.3%”。

两次运行日期不同，虽然模型别名都是 `deepseek-flash`，但没有冻结供应商权重；Schema、提示词和执行策略也发生了变化。因此这是历史开发记录对照，不是严格的单变量 A/B 实验。新旧预览和审查阶段也不是同一种端到端测量，不能简单拼接数字来宣称整体提速。

## 2. 旧版为什么会消耗一千多万输入 token

旧版一开始发送完整 diff 与文件清单。之后每调用一次工具，就把结果追加到消息历史，下一轮又把整个历史发送给模型。

```text
第1轮：提示词 + 完整diff
第2轮：提示词 + 完整diff + 第1次工具结果
第3轮：提示词 + 完整diff + 第1次工具结果 + 第2次工具结果
……
```

FunASR 历史轨迹还有两个放大因素：

1. 模型又调用了一次 `get_diff`，把初始消息已有的完整 diff 再加入历史。
2. 后续工具返回整个文件，49 次全文读取让历史持续增长。

所以，1,134 万是**多轮输入累加值**，不表示仓库本身就有一千多万 token。

如果初始上下文大小记为 `D`，第 `i` 次工具结果大小记为 `R_i`，一共调用模型 `N` 次，那么输入开销可粗略理解为：

```text
累计输入 ≈ N × D + Σ[(N - i) × R_i] + 提示词、协议等其他开销
```

越早进入历史的大段内容，会被后面的请求重复携带越多次。本轮优化重点就是减少这种重复传输，并约束调查范围。

## 3. 优化一：按变更分批，每批使用独立上下文

### 旧版做法

一个模型循环负责整组变更，所有调查结果都积累到同一段历史中。模型自己决定继续查什么，也容易不断扩展调查范围。

### 新版做法

`review_plan()` 从代码的实际变更及附近上下文生成计划，保留新旧行号；每批最多五个文件，紧凑变更表示目标约两万字符。过长而无法纳入的行明确记录为未覆盖。

`review_repository()` 为每一批创建独立的模型实例与消息历史。一个批次完成后，程序保留它的结构化结论，下一批不再携带前一批的全部工具记录。所有批次最后由程序校验、去重和合并，不额外让一个模型重读完整调查历史。

```text
第一批：本批diff → 必要工具查询 → 本批结论
第二批：本批diff → 必要工具查询 → 本批结论
……
程序合并各批结论，并列出没有完成的范围
```

### 为什么有帮助

每轮不再重复携带整组 diff 和此前所有文件内容。这是降低上下文重复量的主要设计变化之一，也让任务进度与未完成范围变得明确。

### 代价与边界

跨批次的逻辑联系可能被削弱，因此仍允许搜索、查定义和读取关联文件。分批本身不能保证关键关联一定被找到；它也不是跨批次的完整语义分析。

**这里没有改成只从 Git 加载变更文件。** 服务端仍加载同样的 174 个白名单文件，供后续查询使用；变化的是发送给模型的内容及任务组织方式。

代码位置：[retrieval.py](../retrieval.py) 的 `review_plan()`；[managed_review.py](../managed_review.py) 的 `review_repository()`。

## 4. 优化二：紧凑 diff，减少表示本身的开销

第一版分批计划为每一行重复传输类似下面的 JSON：

```json
{"kind":"add","old":null,"new":213,"text":"return result"}
```

最终版通过 `compact_changes()` 转成带真实新旧行号的紧凑表示：

```text
+-:213 | return result
```

这里 `+` 表示新增，冒号前为旧行号、后为新行号，`-` 表示该版本不存在。模型引用证据时仍需填写原始代码，不包含这些标记。

服务端继续保存结构化行数据用于证据检查，只有发给模型的表示变紧凑。这样减少了重复字段名，也能在同样的输入目标内组合更多变更，将这组输入的计划从 14 批调整为 8 批。

**这是文本表示优化，没有训练或压缩模型，也不是通过删掉原始代码行来获得更好数字。** 评审范围调整与超长行未覆盖都有单独记录。

代码位置：[retrieval.py](../retrieval.py) 的 `compact_changes()`。

## 5. 优化三：把全文读取改成有限片段读取

旧版 `read_file` 默认把整个文件送回模型。新版仓库引擎允许指定 `start_line`、`end_line`，单次最多返回 80 行，并限制返回字符量。

例如，要检查第 200 行附近的错误处理，可以请求：

```json
{
  "action": "read_file",
  "arguments": {
    "path": "service.py",
    "version": "after",
    "start_line": 180,
    "end_line": 230
  }
}
```

返回结果包含真实行号、实际展示行、是否有省略、文件总行数及下一段起点。请求超过 80 行时不会全部返回，需要根据 `next_line` 继续读取。超长行不会以半截内容冒充完整证据。

同时增加两类定位手段：

| 定位方式 | 作用 | 当前限制 |
| --- | --- | --- |
| BM25 + 字面量加分 | 按关键词与标识符检索相关代码、文档片段 | 仓库引擎最多返回2段，每段有限行数和字符数；不保证语义相关代码一定被召回 |
| AST 定义索引 | 根据函数或类名定位定义 | 返回有限定义片段，不是完整类型推断或跨文件符号解析 |

这些机制让模型更容易获取局部相关内容，避免为了找一个定义就把大文件全文带入历史。但本轮没有做独立的检索召回率实验，不能宣称检索准确率已经提高。

当前没有引入 Embedding、向量数据库或跨任务增量索引。

代码位置：[retrieval.py](../retrieval.py) 的 `code_window()`、`CodeIndex`；[managed_review.py](../managed_review.py) 的 `BoundedTools`。

## 6. 优化四：避免重复内容再次进入历史

新版对已经提供的内容做明确处理：

- 初始输入已经包含本批 diff，提示词要求直接分析；再次请求 `get_diff` 时只返回“已在上下文”的说明，不重复附上 diff。
- 当前批次内相同参数的查询再次出现时，通常返回已有结果提示，避免重新附上同样的大段文本。
- 不可用资源继续使用原有记录，避免反复尝试读取。

该查询记忆主要针对**当前批次**。新批次具有独立历史，必要信息仍可能再次提供；不能为了少传内容，让一个从未看过它的新模型实例只拿到空缓存引用。

它也不同于供应商的前缀缓存。供应商缓存命中可能影响计费与处理方式，但重复内容仍会反映在累计输入 token 中。新版本记录到了缓存命中量，未据此补造旧版费用。

代码位置：[managed_review.py](../managed_review.py) 的 `BoundedTools.begin()` 和 `execute()`。

## 7. 优化五：按实际延迟分配预算，并预留结论阶段

这是从第一轮失败中补上的改进。

首次分批已经把已记录输入降到 164,071 token，却仍在 300 秒超时，只交付 8/14 批。原因是请求通常耗时约 10–14 秒，串行请求数量仍然太多。

最终版根据最近最多8次已返回请求的平均耗时，估算剩余时间还能承受多少次调用；尚无观测值时使用12秒作为初始估计，再结合剩余批次数分配机会。单批最多4次调用。

```text
剩余可用调用 ≈ min(剩余次数上限, 剩余时间能够容纳的调用数)
本批调用机会 ≈ 剩余可用调用 / 剩余批次数
```

每批最后一次机会切换到只允许 `final` 的结构约束，要求依据已展示内容提交结论或说明限制。模型若仍输出工具动作、给出错误证据，或接口失败，该批会保持未完成；程序不会替它生成一个成功结论。

总体保护包括：

| 保护项 | 当前设置与语义 |
| --- | --- |
| 模型调用 | 最多50次，可以提前完成 |
| 审查总时间 | 300秒；仓库预览在审查循环之前 |
| 单次模型请求 | 最长60秒，同时受任务剩余时间约束 |
| 单请求大小预检 | 64,000字节保护线；消息UTF-8大小加协议余量的保守估算 |
| 累计输入预算预检 | 已知输入量加下一次保守估算接近600,000时停止 |

字节预检不是精确 tokenizer，也不是供应商账单硬限。实际 token 始终以接口返回的 `usage` 为准；接口没有返回的用量标为未知。

这一改动帮助最终试验交付了8批代码范围，但一次完成不能证明以后都能完成。它主要改善任务安排与终止行为，不能替代缺陷质量验证。

代码位置：[managed_review.py](../managed_review.py) 的 `review_repository()`。

## 8. 优化六：批量读取 Git，缩短网页预览等待

这一项主要优化本机加载，不直接改变模型的推理能力。

旧版为每个文件单独启动一次 Git 读取对象。新版先筛选文件，再通过 `git cat-file --batch`，每次最多读取20个对象。

以一个包含174个合格文件的快照为例，读取文件内容的 Git 启动次数可以从174次减少到约9次；其他提交解析和文件清单查询仍然存在。

读取过程仍检查对象编号、类型、大小、数据边界与额外内容；数据集、权重、用户排除项仍先过滤。最终快照文件数与字节数没有因这项优化而缩小。

本次网页预览记录从30.14秒降到2.56秒。减少进程启动开销是对应的机制，但系统缓存、运行日期等也可能影响耗时，不能把一次测量当作所有仓库的固定加速倍数。

代码位置：[git_input.py](../git_input.py) 的 `blob_stream()` 和 `snapshot()`。

## 9. 可靠性改进：证据台账与可解释的未完成状态

旧版已检查文件、行号和证据原文是否匹配。新版进一步使用 `EvidenceLedger`，记录当前批次真正展示过的代码行：初始变更中的新版本代码行，以及工具实际返回的原文行。

一个引用即使在仓库中确实存在，如果它没有完整展示给当前批次模型，也不能直接作为已接受的报告证据。

同时，结果会区分：

- 已交付哪些批次、哪些代码文件。
- 哪些文件仅作上下文。
- 哪些批次、文件或变更行未完成。
- 模型因次数、时间、上下文、输入预算或接口错误中的哪一种原因停止。

**这改善的是可追溯性，不是自动证明缺陷成立。** FunASR 新版报告提出1条候选，代码助手静态查看被调用的发送函数后发现，首包状态实际会被更新，原报告的关键推断不成立。本条没有计入确认缺陷，原始输出和反证分别保留，尚未经项目开发者确认。

因此，不能把“JSON合法、行号正确、原文存在、已交付报告”合并理解为“缺陷已经验证”。

代码位置：[retrieval.py](../retrieval.py) 的 `EvidenceLedger`；[managed_review.py](../managed_review.py) 的结果合并与范围统计。

## 10. 可观测性改进：能解释实际消耗来自哪里

新结果保留每轮调用的批次、已返回输入/输出 token、可取得的缓存命中信息、耗时及请求大小，并显示在执行记录和最终报告中。

最终 FunASR 试验的输入拆分为：

```text
缓存命中输入： 75,648 token
未命中输入：  117,126 token
累计输入：    192,774 token
```

这些数据让我们能识别“输入变小但请求延迟仍高”等问题。它们本身不是让模型更聪明的功能，而是支撑优化决策的证据。失败请求若没有返回用量或耗时，不复用上一轮记录，也不假装消耗为零。

## 11. 哪些结论可以写，哪些目前不能写

可以据实表述：

> 项目针对代码审查中完整历史反复发送、调查难以收尾的问题，实现了变更分批、有限片段检索、证据台账和延迟感知预算控制。在固定FunASR提交的历史参考对照中，累计输入由约1,134万降至19.3万token，25次调用交付8批代码范围报告；同时保留范围变化、失败试验与候选反证记录。

目前不支持的结论包括：

- “缺陷识别准确率提高98.3%”：98.3%是记录到的输入量下降比例。
- “费用降低98.3%”：旧版缺少对应缓存拆分，没有做金额核算。
- “模型审查整体提速十几倍”：明显变快的是本地预览，模型阶段没有提速。
- “28个代码文件100%没有问题”：批次交付不代表验证所有执行路径。
- “某一个组件单独带来了全部提升”：没有做控制其他变量的组件消融实验。

三个已知开发样例的真实回归中，两个预置缺陷被正确描述，正常重构没有告警。这支持基础能力仍可工作，但样例已用于开发，不能据此计算通用准确率。

下一步优先补充新的独立缺陷案例、关键证据检索评估，以及候选问题的调用链反证复核，再判断节省输入是否以漏报或误报为代价。
