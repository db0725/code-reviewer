# 项目主线与下一阶段

面向硕士秋招，项目的核心价值是：把模型的代码理解能力变成有范围、有证据、有预算、可评估的审查服务。目标不是宣称能发现所有缺陷，而是能解释系统做了什么、漏掉了什么、为什么失败、优化带来了什么代价。

## 第一阶段：有边界的仓库审查

本轮实现内容：

- 用 Git 批量对象读取替代逐文件启动 Git，仍固定提交、过滤数据与权重、保持文件校验信息。
- 按变更附近的行生成计划；Python 与 Shell 代码进入审查批次，其他白名单文本只作为契约上下文。计划中的未覆盖行单独记录。
- 每批独立消息历史，最多五个文件、约两万字符的紧凑变更；主机保留结构化行号供校验。
- 按行读取最多80行；BM25 片段检索与 AST 定义索引只返回有限原文。重复请求不再次塞入大段内容。
- 使用证据台账，要求报告所引原文确实展示给当前批次模型。
- 同时限制调用次数、时间、单请求预检大小和累计输入量；根据已观察到的延迟安排余下批次的调用机会。
- 给每批预留提交结论的机会。拒绝提交、接口失败、超时或证据错误，都保留未完成范围，不自动认定代码无缺陷。
- 展示批次、资源限制和接口返回用量；保留每轮输入、输出、缓存命中信息和耗时供分析。

这些能力是上下文工程、检索增强和 Agent 执行控制的基础。当前检索使用 BM25 与 AST，没有向量数据库；任务仍在单进程内存中运行，不是多用户生产服务。

## 第二阶段：把效果评测做扎实

本轮已接入候选复核，并新增12个合成案例（4开发、8保留），保留组首次运行完成。机制见[候选复核设计](CANDIDATE_VERIFICATION.md)，结果与边界见[实测记录](../tests/VERIFICATION_RESULTS.md)。后续需要扩大独立样本与真实仓库验收，已观察过的保留组不能继续当作未见数据。

优化前后需要同时评估完成情况、报告语义、耗时与 token。用量下降但漏报更多，也可能是退步。

1. 在已有冻结案例之外增加新的独立案例，覆盖跨文件接口变更、错误处理、异步状态与配置行为。
2. 给每个缺陷定义触发输入、失败行为和独立验收依据，区分“命中行号”和“正确解释缺陷”。
3. 在相同提交、模型标识、范围和预算下重复试验；记录范围、协议、预算或模型版本变化，避免不公平比较。
4. 评估检索是否取回关键证据，再评估最终报告，定位失败来自检索、推理、输出结构还是执行控制。

已有三组内置示例可以通过 `tests.evaluate --engine managed --mode real` 做开发回归；它们已在开发中使用，不是独立保留集。独立基准仓库的原始冻结数据和历史结果不改写。

## 第三阶段：补齐可交付能力

核心效果稳定后，再依次补上任务持久化、取消与恢复、部署配置和自动回归。随后接入真实 GitHub PR，增加可复核的使用反馈。生产化要有实际验证，不能仅因增加 Dockerfile、数据库或框架名称就写成“高可用平台”。

框架迁移、向量检索、多 Agent 都应由明确瓶颈驱动。例如，关键词检索确实遗漏语义相关的代码时，再比较语义检索和混合检索；单批调查确实需要不同职责协作时，再研究多 Agent。

## 你可以怎样学习

先按 `managed_review.review_repository()` → `retrieval.review_plan()` → `BoundedTools` → `EvidenceLedger` 阅读。然后自己修改一个预算、增加一个边界检查，并观察固定响应检查如何变化。最后读真实轨迹，对照“模型想做什么”和“主机实际允许了什么”。

阅读代码时优先回答：为什么需要这条约束？它防住哪类失败？会不会引入漏报？怎样验证它有效？这些答案比列出技术名词更能体现项目深度。
