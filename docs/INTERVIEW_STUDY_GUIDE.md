# Code Review Agent：不看代码也能讲清楚的面试学习手册

适用版本：截至 2026-11-07 的本地 Demo，仓库审查入口为 `review-and-verify-v3`，发现阶段为 `bounded-batches-v2.1`，候选复核为 `counterevidence-v2`。

这份文档按当前实现和已保存的实验记录编写。本轮只整理学习材料，没有修改运行逻辑，也没有重新调用模型。文中的测试数字是上一轮验证记录，不代表今天重新跑过。

## 1. 先用一句话说清项目

> 我做的是一个面向 Python 代码变更的本地审查 Agent：读取固定 Git 提交，按变更分批，让模型按需搜索和查看相关代码，再对候选问题补充调用与旧版证据进行复核，输出带文件、行号、触发条件和证据的报告，同时控制调用、时间和输入预算。

可以把它理解成一名“有工具、有规定工作范围、需要提交证据的审查助手”。

普通聊天通常是：你把代码贴给模型，模型一次回答。这个项目多了三层工作：

1. **获取信息**：模型可以决定还需要查看哪些代码，程序执行只读工具，把结果交还模型。
2. **约束过程**：程序检查动作格式、路径、原文证据和预算，限制反复调查与越界访问。
3. **检查结论**：候选进入独立上下文，结合修改前后代码寻找反证；证据不足时保留“待核实”。

面试时先讲用户问题和完整流程，再讲技术。不要开口只说“用了大模型、RAG、Pydantic”。

## 2. 目前能做什么、做到什么程度

### 2.1 已实现的用户功能

| 功能 | 通俗解释 |
| --- | --- |
| 本地网页工作台 | 左侧选输入，中间看代码，右侧看调查轨迹与报告 |
| 三个内置小示例 | 两个预置缺陷和一个正常重构，用于演示和开发回归 |
| 本地 Git 仓库审查 | 比较两个已提交版本，也支持从空版本开始的首次导入审查 |
| 预览固定版本 | 开始前确认提交、文件范围、排除项和资源说明 |
| 分批调查 | 较大变更拆成有限批次，每批使用独立消息历史 |
| 按需取证 | 按行读文件、关键词片段检索、定位函数与类定义 |
| 候选复核 | 补充调用方、被调用方、装饰器、状态更新和旧版证据 |
| 三类复核结果 | 模型支持、已有反证、待核实；保留原始候选 |
| 资源缺失说明 | 声明数据集和权重未提供，设置排除路径，避免反复寻找不可用资源 |
| 实时执行轨迹 | 展示批次、模型决策、工具结果、校验反馈和预算 |
| 证据定位与下载 | 查看对应代码位置，下载 Markdown 报告 |
| 明确的离线回放 | 无密钥时演示页面；它是固定脚本，不能用来证明模型效果 |

### 2.2 必须记住的版本差异

**本地 Git 仓库默认走“分批发现＋候选复核”。内置示例和网页回放仍走原来的小示例循环。**

不能因为仓库入口升级，就说每个入口都运行了完整复核。命令行也保留显式的旧版或关闭复核对照方式，用于实验。

### 2.3 目前的边界

| 边界 | 面试中应该怎么说 |
| --- | --- |
| 以 Python 静态审查为主 | Python 使用 AST；Shell 变更可进入批次，但没有同等的 AST 语义能力 |
| 不执行外部仓库 | 不运行训练、测试、脚本或模型生成代码，也不自动修改代码 |
| 不验证数据和权重 | 用户说“已提供”，也不等于系统实际读取或验证了资源 |
| 删除文件锚定未支持 | 当前有明确限制，不能说覆盖所有 Git 变更类型 |
| 调用关系是静态线索 | 按名称和包路径邻近性匹配，无法完整解决动态分派与类型绑定 |
| 本地单用户服务 | 同一时间只运行一个审查任务；批次和模型请求串行执行 |
| 任务保存在内存 | 最近最多 30 个任务，重启后清空；刷新恢复不等于跨重启恢复 |
| GitHub PR 未接入 | 目前是本地提交比较，没有自动发 PR 评论 |
| 没有向量数据库或模型训练 | 当前检索为 BM25、字面匹配加分和 AST 定位；没有 embedding、微调、多 Agent 框架 |

## 3. 一次审查是怎样完成的

用“订单折扣函数改动”为例：修改把“折扣比例”错误地当成“折扣金额”。单看一行调用不一定能发现，需要找到被调用函数的返回值约定。

```text
选择仓库、前后提交、项目说明
        ↓
固定提交快照，筛掉数据、权重和排除项
        ↓
生成带新旧行号的 diff，拆成有限批次
        ↓
模型看当前批次，提出下一步动作
        ↓
严格校验动作 → 执行只读工具 → 回填相关代码
        ↖ 必要时继续调查，受预算控制
        ↓
提交候选问题，核验位置、原文、可见范围并去重
        ↓
程序组装候选、调用关系和旧版行为的证据包
        ↓
独立上下文复核：支持 / 反驳 / 不确定
        ↓
展示报告、限制与执行记录，允许下载
```

这里有两个不同的“循环”：

- **发现阶段**：模型可以选择代码工具，多轮补充信息。
- **复核阶段**：程序先构造有限证据包，模型据此给判断；它不再自行无限调用代码工具。校验不通过时最多有限次纠正。

“模型判断”和“程序执行”必须分开理解。模型生成一个读文件动作，并不表示它已经读到了文件，只有宿主检查通过并返回内容后，信息才真正进入上下文。

## 4. 必须掌握的基础知识

### 4.1 大模型请求、消息历史与 Token

**消息历史**是模型这一次请求能看到的输入，包括系统规则、任务、此前动作和工具结果。接口本身不会替应用保存你想象中的全部记忆，应用需要组织并发送相关历史。

**Token** 是模型计量输入、输出的基本单位，不等于字符、单词或文件字节。中文、英文、符号和代码的切分不同，不能把“20 KB 代码”直接说成“20K Token”。

需要区分四个量：

| 概念 | 含义 |
| --- | --- |
| 本地快照大小 | 服务端保存了多少代码文本 |
| 单轮输入 Token | 某一次请求实际发送并被接口计量的输入 |
| 累计输入 Token | 一次任务所有请求输入量的总和，重复发送也会累计 |
| 输出 Token | 模型生成的动作参数、报告与解释等内容 |

为什么小仓库也可能消耗很多 Token？因为相同 diff 和越来越长的历史会被一遍遍发送。

简化理解：固定上下文为 F，每轮新增内容约 C，调用 n 次，总输入大致为 `n×F＋C×n×(n－1)/2`。实际消息长度并不均匀，这个式子只说明“重复历史累积”的趋势，不能拿来替代真实 usage。

**当前处理方式**：快照保留在服务端；每批只给必要 diff，相关文件按需返回有限原文；批次之间不累积完整聊天历史。

### 4.2 温度、输出长度与确定性

温度可以理解成对采样随机性的调节。当前请求配置温度 0.2、关闭思考、最大输出 2,400 Token。

低温度有助于减少波动，但不保证事实正确、格式永远正确，也不能保证多次调用完全相同。“关闭思考”是本项目的接口参数设置，不代表模型失去分析能力，也不是获得了可检查的内部推理过程。

最大输出长度是上限，不是每次固定生成这么多。输出达到上限可能被截断，截断动作不能直接执行。

### 4.3 JSON、JSON Schema、Pydantic 分别是什么

| 名称 | 通俗解释 | 能保证什么 |
| --- | --- | --- |
| JSON | 传递对象、数组和字段的一种文本格式 | 能被 JSON 解析器读懂 |
| JSON Schema | 对 JSON 字段、类型、枚举和分支的结构约定 | 描述“应该长什么样” |
| Pydantic | Python 中定义和验证数据结构的库 | 接收后检查是否符合本地类型与字段约束 |

三种结果要分清：

- 返回一段合法 JSON，但动作是不存在的 `delete_repo`：语法合法，业务动作不合法。
- 动作为 `read_file`，行号却是字符串“10”：本项目严格类型校验不接受。
- 结构、行号和代码原文全部正确，解释却误解了函数：结构和引用合法，语义仍可能错误。

### 4.4 Git 的提交、快照、diff 与行号

**提交**指一份被版本管理记录的状态；分支名和 HEAD 可能变化，完整提交编号用于固定本次输入。

**快照**是某次提交中的文件内容集合。本项目从 Git 对象中读取，不通过切换分支获取代码，也不使用未提交工作区文件。

**diff**是前后版本差异。删除行属于旧版本，新增行属于新版本，普通上下文行可能在两个版本中有不同的行号。报告必须说明引用哪个版本，不能把旧版第 20 行直接定位到新版第 20 行。

首次导入是“空快照 → 首次提交”。这时可以做新增代码初审，但没有真实旧实现可以证明某风险是此次修改引入的历史回归。

### 4.5 HTTP、后台任务与 SSE

网页创建任务后，服务端先返回任务编号和 HTTP 202，再用后台线程执行耗时审查。网页不用一直等同一个创建请求完成。

SSE 是服务端通过 HTTP 持续单向发送事件，浏览器使用 EventSource 接收。当前事件有编号；连接中断后，可以按 Last-Event-ID 补发已有事件，前端也按事件编号去重。

**SSE 实时事件不等于模型文本流式输出。** 当前模型请求配置 `stream=false`，必须收到完整动作才能校验执行；页面实时展示的是任务和工具事件。

为什么没有用 WebSocket？当前主要需要服务端向网页推送进度，单向 SSE 足够；双向持续通信不是这个版本的必需能力。

### 4.6 Python 线程、锁与条件变量

当前服务使用标准库 ThreadingHTTPServer，可以同时处理查看结果和事件连接等 HTTP 请求；但业务规则限制同时只审查一个任务。

- 锁用于保护任务集合，避免两个请求同时通过“当前没有任务”的检查。
- 条件变量用于等待新事件，产生事件时唤醒 SSE 连接；无需不停轮询事件列表。
- 网络请求放入工作线程，主流程按剩余时限等待，超时后停止接受结果。

要理解一个限制：**主流程超时不等于远端请求一定被取消，也不保证远端没有计费。** 当前没有完整的远端取消机制；未返回 usage 时消耗标记未知。

### 4.7 静态分析、动态验证与 AST

静态分析是“不运行程序，检查源码结构和逻辑”；动态验证是“运行程序或测试，观察具体输入下的行为”。

AST 是抽象语法树，可以把代码解析成函数、类、调用、装饰器等结构。它比只找 `def` 字符串可靠，因为注释、字符串和真正定义可以区分，且能获取起止行号。

但是，解析到 `obj.send()` 只说明有一个名为 send 的调用，不能单靠 AST 就确定 obj 在运行时是哪一种类型。当前项目提供的是静态定义与调用线索，不能说已经实现完整跨文件语义分析。

## 5. 进阶技术一：显式 Agent 工具循环

### 5.1 它为什么是 Agent

系统有明确目标，模型根据当前证据选择下一动作，宿主执行工具，把观察结果交回模型，再继续决策，直到提交结果或触发限制。

它具有“决策 → 行动 → 观察 → 再决策”的形式，可以说与 ReAct 的思想相近。但不要说实现了某个专有 ReAct 框架，也不要把内部推理过程描述成已经可见或已被保存。

### 5.2 四个工具与传输函数的区别

| 内部动作 | 作用 | 当前仓库入口的实际限制 |
| --- | --- | --- |
| get_diff | 获取变更 | 当前批次初始消息已给 diff，重复请求只提示复用 |
| read_file | 读取前后版本代码 | 按行返回，每次最多 80 行，还受字符上限约束 |
| search_code | 搜索相关代码片段 | BM25 加字面匹配加分，最多返回 2 个受限片段 |
| find_definition | 定位 Python 函数或类定义 | AST 索引，仓库入口最多返回 1 个定义片段 |
| final | 提交候选报告 | 它是结束动作，不是代码读取工具 |

接口层让模型调用的是 `review_step`，其参数里再放一个动作。它是统一的决策传输函数，**不是给模型五种任意执行权限**。实际动作由宿主分发到白名单工具。

复核使用另一个传输函数 `verify_candidate`，仅提交复核结论。

### 5.3 谁控制结束

模型可以提交 final，程序也可以因预算、错误、重复调用或证据问题停止。可靠性不能只依赖提示词里写“不要循环”。

原版循环对连续格式错误、相同动作及工具失败设置退出条件；资源缓存还有同一不可用路径的累计请求保护。当前分批引擎进一步限制每批最多 4 次模型调用，重复查询不再重复回填长内容；最后一次机会要求提交结论。两个入口的细节不同，不能把旧版所有退出计数直接套到新引擎。

### 5.4 为什么没有引入 LangGraph

当前工作流是有限阶段加显式循环，Python 足以表达状态、预算和错误路径。这样容易展示“哪个动作被允许、为什么退出、哪段证据被看过”。

代价是状态和恢复逻辑需要自行维护。以后若出现复杂分支、人工审批、持久化检查点和多职责协作，可以再评估框架收益；当前没有把框架名作为技术深度来源。

## 6. 进阶技术二：严格函数调用＋Pydantic 双层约束

### 6.1 为什么只写“请输出 JSON”不够

提示词是要求，不是接收端的验证器。模型仍可能附加解释、遗漏字段、返回错误动作，或者在多轮工具交互中输出不符合接口协议的内容。

本项目默认通过 DeepSeek Beta 严格函数调用传输动作：函数启用 strict，强制选择指定函数，并在本地继续校验完整参数。

### 6.2 两层分别干什么

**远端结构约束**：约束对象形状、必需字段、枚举、动作分支，禁止未定义字段。

**本地 Pydantic 校验**：严格检查完整响应、类型、字符串长度、正整数行号、数组数量等。不同动作使用 `action` 判别分支，读文件动作不能混入最终报告字段。

模型接口只支持 JSON Schema 的一部分，因此本项目从同一套 Pydantic 定义生成远端兼容子集，把远端不支持的长度、范围等约束留在本地检查。远端 strict 不等于本地全部约束都已被执行。

这是**数据契约的一处定义、两端检查**，减少提示词、接口与本地结构各自维护造成的不一致。

### 6.3 多轮里为什么要保留 tool_call_id

原生工具调用带有调用 ID，工具结果必须携带对应 ID，模型接口才能知道“这份结果回答的是哪一次调用”。

当前适配层把内部动作历史还原成原生 assistant/tool 消息并保留原始 ID。只把结果拼成普通用户聊天，可能让多轮协议与模型预期不一致。历史开发中，单轮结构探针通过并没有保证多轮稳定，补齐原生配对后才完成开发组复测。

### 6.4 出错后怎么处理

完整响应不合法就拒绝接受，返回有限错误位置和类型，允许预算内纠正。不从解释里截取“看起来像 JSON 的一段”，不自动转换不合法字段，不把多个动作中的第一个当成功。

拒绝、截断和接口错误明确记录；不会悄悄切换离线回放或另一协议，把一次失败包装成真实模型成功。

### 6.5 这个机制没有解决什么

它解决的是“动作能否安全解析和按约定传输”。代码解释是否正确、是否漏掉关键副作用、业务契约是否满足，必须用取证、复核与评测处理。

**面试回答模板**：

> 我将输出可靠性分成结构和语义两层。结构用严格函数调用加本地 Pydantic；语义上继续核对真实代码、引用可见范围，并补充独立上下文复核。结构通过不能当成缺陷已经成立。

## 7. 进阶技术三：轻量代码 RAG 与上下文工程

### 7.1 RAG 在项目里到底用在哪

RAG 的核心是“先从外部资料检索相关内容，再把内容提供给模型生成判断”。外部资料在这里是当前 Git 快照中的代码。

本项目已经具备轻量代码检索增强：模型提出查询 → BM25 或 AST 返回代码原文 → 原文进入下一轮上下文 → 模型继续分析。复核阶段也由程序补充调用与旧版证据。

它使用**词法检索和结构定位**，没有使用 embedding、向量数据库、语义重排或图数据库。可以说“轻量代码 RAG”，随后必须说明具体是 BM25＋AST，避免让面试官误以为做了向量检索。

### 7.2 BM25 要理解到什么程度

BM25 给每个代码片段打相关性分数，主要考虑三点：

1. 查询词在片段中出现得越多，通常越相关，但收益会逐渐饱和。
2. 在整个集合中很常见的词辨识度低，罕见的标识符权重更高。
3. 长片段天然容易包含更多词，需要长度归一化。

本项目将代码切成约 60 行的片段，相邻片段有约 8 行重叠；索引内容包含文件路径与代码。分词保留标识符并拆分下划线，过滤部分常见词；查询字面量完整出现时额外加分。

如果被问公式，理解各变量即可：

```text
score(q,d) = Σ IDF(t) × f(t,d)×(k1+1)
                        ─────────────────────────────────────
                        f(t,d)+k1×(1-b+b×len(d)/avg_len)
```

这里 t 是查询词，d 是片段，f 是词频，IDF 表达稀有度，len 是片段词数，avg_len 是平均长度。当前实现 k1=1.2、b=0.75，外加字面量加分；不是训练得到的参数，也没有宣称这两个值对代码检索最优。

### 7.3 为什么先用 BM25，没有直接用向量库

代码中的函数名、字段名、异常名常常是很强的检索线索；当前范围有限，内存索引容易建立，也容易解释为什么取回这段代码，不需要额外 embedding 请求和向量服务。

代价是对同义描述、行为相似但名称不同的实现不够敏感。将来若评测证明关键证据因为词汇不同而漏取，可以比较词法与向量混合检索；当前没有这项收益数据。

AST 主要弥补“我知道符号名，但需要找到真正定义和范围”的需求。它是结构定位，不是把 BM25 变成完整语义搜索。

### 7.4 分批为什么能省输入

旧版把完整 diff 和增长的历史持续带入下一轮，已经看过的内容反复计入输入。

当前做法是：

- 按代码变更附近的行生成批次，保留真实的新旧行号。
- 每批最多涉及 5 个文件，紧凑 diff 约 20,000 字符；这些是分组约束，不是模型 Token 数。
- 每批独立消息历史，历史不跨批无限累积。
- 全文留在服务端，工具只返回受限片段。
- 重复查询提示复用已有结果，不再次回填大段代码。
- 极长行或未完成批次明确列出，不能截断后声称全部覆盖。

文档与配置说明可以作为契约上下文，但当前默认不会把它们单独作为代码批次审查。实际纳入代码批次的是 Python 与 Shell 变更。

### 7.5 代价是什么

独立批次减少历史，却可能丢失跨批信息；片段上限控制输入，却可能漏掉函数尾部的状态更新；关键词检索便宜可解释，却可能漏掉语义相关代码。

候选复核会补充部分跨调用和旧版证据，但不能保证补齐所有缺失信息。要同时观察成本、完成率和漏报情况，不能只看 Token 下降。

## 8. 进阶技术四：证据台账与候选复核

### 8.1 为什么“引用的代码存在”还不够

假设模型说某函数没有更新状态，引用的三行代码确实存在，但状态是在稍后调用的另一个函数里更新的。

这说明：

- 原文真实，只能证明模型没有凭空编造那几行。
- 引用完整，也只能证明它看过这几行。
- 这些事实不能证明它理解了全部执行路径。

所以本项目把检查分成三个层次：

| 层次 | 检查内容 | 不能由此推出的结论 |
| --- | --- | --- |
| 结构 | 字段、类型、分支和长度等是否合法 | 缺陷真实 |
| 来源与可见性 | 文件、版本、行号、完整引用是否匹配；是否展示给该次模型 | 因果解释真实 |
| 语义复核 | 机制、引入性、具体影响是否获得证据支持，有无反证 | 完成了运行证明或穷尽审查 |

### 8.2 Evidence Ledger 是什么

它是程序维护的一份“当前批次模型实际看过哪些代码行”的台账，不是另一个大模型。

初始 diff 和工具返回会登记已展示行。报告的主证据和关联引用不仅要在快照中存在，还必须完整落在当前批次已展示范围内。原文按完整行核对，允许省略缩进等首尾空白，不是任意片段命中，也不是字节完全相等的密码学证明。

这能拦住“引用真实文件里的未读代码”或错位引用。它无法拦住所有“读到了但理解错了”。

当前主锚点要求位于本次修改的文件，发现阶段还限制在当前批次文件；不能夸大成程序已经形式化证明缺陷一定落在新增行上。是否由本次修改引入，要在复核里继续比较。

### 8.3 复核为什么使用独立上下文

发现模型已经形成一个解释，沿用整段发现对话容易继续为原结论寻找理由。复核给新上下文一个固定候选与证据包，明确要求寻找反证。

**独立的是任务上下文，不是模型来源或独立真值。** 当前默认仍调用同一配置模型，同样可能出现相关错误，不能说“两位不同专家投票证明了结论”。

### 8.4 证据包是怎样构造的

程序先放入原始候选、锚点和引用，再尝试取回：

- 修改后包含该位置的函数；
- 旧版本对应函数及旧版被调用函数，包括新版已经删除的调用；
- 被调用函数、装饰器与可能更新相关状态的实现；
- 调用方等辅助线索。

匹配依赖 AST 名称和包路径邻近性；有歧义时保留限制。长函数会尝试展示头尾，避免只读开头漏掉尾部状态更新，但中间省略部分仍明确记为缺口。

证据包上限约 42,000 UTF-8 字节，完整请求还有 64,000 字节预检。证据有限时允许不确定，不能因为包组装完了就声称调用链完整。

### 8.5 三个必要判断

| 判断 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 故障机制 | 候选声称的因果链是否成立 | 状态是否真的没有更新？ |
| 变更引入性 | 这个风险是否由本次修改引入 | 旧版是否也有相同行为？ |
| 具体影响 | 什么输入会产生什么错误结果 | 重复请求是否会再次产生副作用？ |

整体支持必须三项都支持并有支持证据；整体反驳至少要有关键判断被否定并提供反证；不确定必须说明缺失条件。程序检查这些字段的一致性，但字段之间逻辑一致仍不保证模型判断真实。

复核引用需标记 before/after，核对真实快照与本次证据包的展示范围。不能引用包外的知识片段伪装成本次代码证据。

### 8.6 为什么保留“不确定”

静态代码可能不足以确定动态类型、外部契约或真实数据条件。强制二选一会把不充分证据变成确定告警或确定否定。

当前原始候选不会因复核失败而消失。默认最终问题列表收录有效复核支持项，反证和待核实项分别展示；超时、接口错误、未执行和证据不合法保留具体原因。存在待核实时，不能展示成一次完整的零问题审查。

这是一种**允许拒绝判断的设计**，目前没有训练概率校准模型，也没有用模型自报置信度决定真假。

## 9. 进阶技术五：共享预算与失败处理

### 9.1 当前关键预算

| 层级 | 默认限制 | 意义 |
| --- | --- | --- |
| 单次仓库任务 | 50 次模型调用，300 秒总时限 | 发现和复核共同使用，不是各自 50 次、各自 5 分钟 |
| 单次模型请求 | 最长 60 秒，受剩余任务时限约束 | 剩余时间不足时取更短时限 |
| 累计输入 | 600,000 Token 预算预检 | 调用前保守估算，调用后用接口 usage 统计 |
| 单次上下文 | 64,000 UTF-8 字节预检 | 有限请求大小保护，不是模型窗口或精确 Token 限制 |
| 分批发现 | 每批最多 4 次调用 | 根据剩余时间和批数可能进一步减少 |
| 候选复核 | 最多 3 个候选，每个最多 2 次尝试 | 高严重级别优先，超出项保留待核实 |
| 本地单版本快照 | 最多 300 文件、单文件 256,000 字节、合计 2,000,000 字节 | 控制读取规模，不等于这些文本全部发送给模型 |

默认总预算下，发现阶段预留 6 次调用、75 秒和 120,000 输入预算给复核，所以默认发现阶段上限是 44 次、225 秒和 480,000 输入预算；复核可以使用实际剩余额度。

“预留”不等于必定消费或固定等待。没有候选时不需要为了用完额度而调用模型。

### 9.2 延迟预算怎么分配

发现阶段根据最近最多 8 次请求的耗时估计后续还能调用几次，再结合剩余批次数分配机会。没有观测时使用默认延迟估计，每批最多 4 次，最后机会要求交付。

这是启发式调度，避免前几批花完全部时间；不是能够精确预测推理时延的调度器，也没有实现并行执行。

### 9.3 为什么用 monotonic 计时

任务时限是持续时间，应使用单调时钟计算绝对截止时间，避免系统时间校准影响剩余预算。每个请求按“60 秒与总剩余时间的较小值”等待。

### 9.4 预检与实际用量怎么区分

当前用 UTF-8 字节加 Schema 余量做保守预检，它不是目标模型 tokenizer 的精确计数，也不是严格费用上限。一个在途请求的实际用量需要等接口返回后才知道。

接口返回的输入、输出、缓存命中和未命中才用于实测统计；没有返回就标记用量未知，不能填成 0。缓存命中属于供应商报告的信息，也不能直接理解成免费或一次请求完全没耗时。

### 9.5 四种任务状态

| 状态 | 含义 |
| --- | --- |
| running | 仍在执行 |
| completed | 在当前有限范围内交付流程完成；不等于证明代码无缺陷 |
| failed | 接口或系统等错误导致失败 |
| limited | 达到预算、存在未覆盖范围或复核不确定等，审查未完整结束 |

**零条告警＋completed** 表示“这个受限流程没有形成支持项”；**零条告警＋limited/failed** 不能被展示或解释为“没有问题”。即使 completed，也不代表发现了所有缺陷。

## 10. 工程基础：资源缺失、安全边界与 Git 加载

### 10.1 数据集没放仓库，怎么通用处理

用户可以声明数据集和权重为未提供、已提供或未知，再补充说明和排除路径。说明与规则随预览固定，改变设置必须重新预览。

运行时只读已经加载的代码快照，不根据 CSV 路径去访问本机图片，不下载数据，不加载权重。图片或权重不在仓库，本身不应当成为代码缺陷；但源码中对缺失文件处理错误，仍可在有证据时报告。

相同“版本＋路径”的不可用资源会缓存原因，重复请求无需重新查找。同一个文件缺失不会推断整个数据集都缺失，更不会把用户声明的“已提供”当成已验证成功。

### 10.2 权限不是靠提示词控制

模型只可以提出白名单动作。宿主检查相对路径、版本、参数和快照成员，不提供写文件、shell 或执行任意代码的工具。

源代码和注释可能包含“忽略前面规则”等提示注入内容，程序把它们当作不可信数据。提示词有帮助，但真正能执行的动作仍由宿主限制；当前不宣称完全抵抗提示注入，也不宣称任意仓库已全面扫描脱敏。

密钥保存在服务端本地配置中，前端不拿到密钥；已知凭证会在事件和报告输出前脱敏。网页使用文本渲染模型内容，避免把模型生成的标签直接作为 HTML 执行。

### 10.3 为什么 Git 加载也值得讲

最初逐文件启动 Git 子进程，文件多时启动开销会累积。当前先列出文件元信息，按类型、排除规则和大小筛选，再使用 `git cat-file --batch` 每批读取最多 20 个对象。

程序核对返回对象编号、类型、声明长度和数据帧边界。批量更快，但解析也必须检查截断、错位或额外数据，避免把错误内容当成正确快照。

这部分是本地 I/O 与子进程开销优化，与模型推理是两个层面的瓶颈。

### 10.4 为什么目前不直接部署公网

当前设计依赖本机仓库路径、单任务和内存状态，监听 127.0.0.1，适用于本地演示。生产化还需要认证、租户隔离、资源与队列调度、任务持久化、数据保护、取消恢复和部署监控。

把监听地址改成 0.0.0.0 并不等于完成了这些能力。

## 11. 指标与评测：这是面试重点

### 11.1 要分开评价哪些能力

| 维度 | 该看什么 | 常见误解 |
| --- | --- | --- |
| 结构稳定性 | 格式反馈、合法响应、任务完成情况 | 没有 JSON 错误就是没有误报 |
| 检索取证 | 是否取回关键调用、旧版行为和反证 | 搜到了很多代码就是检索好 |
| 缺陷语义 | 触发条件、因果链、错误结果是否成立 | 命中预置行号就是找对了问题 |
| 审查完成程度 | 批次交付、待审文件、未覆盖行和待核实项 | 全批次交付就是测试覆盖率 100% |
| 资源效率 | 调用、输入输出 Token、耗时、已知缓存数据 | Token 少必然更快、更便宜且质量不变 |

### 11.2 三类数据要区分

1. **内置示例**：3 个，已经用于开发，适合演示和回归。
2. **原 DKNet 基准**：固定代码上构造 20 个合成修改，10 个缺陷、10 个正常；不是说上游仓库本来就有这 10 个缺陷。结构化改造复测只用了其中相同的 12 个开发案例。
3. **新增独立合成集**：12 个新案例，4 个开发、8 个保留；与前面的案例分开，保留组首次观察前冻结。

这里的“独立”指开发与保留分开、验收答案不进入模型，不是外部第三方盲测，也不能消除人工构造偏差。

### 11.3 什么是独立验收、冻结和泄漏

每个新增微型案例有公开代码和任务描述，也有评测端私有的预期与行为验收。验收检查具体输入下的契约：修改前通过、缺陷版本违反契约、正常改动保持契约。

验收只执行本项目可信的小夹具，不接受外部仓库代码或模型生成代码。不能把它描述成产品已经具备任意仓库自动运行测试能力。

冻结用 SHA-256 记录案例、公开输入构造器和验收程序的摘要；运行结果还记录模型标识、代码摘要、预算与条件。目的是发现数据或程序被改动，不是用哈希证明语义绝对正确。

**泄漏**包括把答案、测试断言或预先写好的候选问题直接提供给本应自主发现问题的模型。当前给定候选复核与端到端发现分开，后者不接收预设候选。

保留组一旦看过结果，就变成已观察数据；后续调参需要新保留案例，不能反复重跑同一组挑最好的成绩。

### 11.4 为什么要做两种评测

**给定候选的复核**：已经给出一个待检查主张，问模型能否根据证据支持或反驳它。这衡量判别，不衡量自主发现。

**端到端审查**：只给代码和公开背景，让模型自己找候选，再复核实际产生的候选。这才包含“能否发现”。

一个复核器可能对已知候选判得很好，但发现器根本找不到这些候选；只报前一项会掩盖漏报。

### 11.5 覆盖率为什么必须和正确率一起看

复核允许不确定。假设 8 例里只判断了 2 例，两例都正确，剩下全不确定：已判别正确率仍为 100%，但不能说 8 例都处理好了。

当前使用：

- 判别覆盖率＝明确支持或反驳的数量 ÷ 计划数量。
- 已判别正确率＝正确判别数量 ÷ 明确判别数量。
- 全部案例匹配率＝正确判别数量 ÷ 计划数量。
- 另外列出不确定、校验失败、接口失败和未执行，不从统计中删除。

常见的缺陷检测指标也要会：Precision＝TP/(TP+FP)，Recall＝TP/(TP+FN)。其中 TP 是正确告警，FP 是误报，FN 是漏报；需要可靠标注和语义匹配，不能用位置命中替代 TP。

真实仓库初审通常没有穷尽真值，因此无法从“报了几条”直接算 Recall；也不能把待核实简单当成正确或错误，应该单列。

## 12. 当前真实结果，应该怎样表达

### 12.1 结构化输出改造：稳定性改善有代价

原 DKNet 相同 12 个开发案例中的 Agent 对照：

| 指标 | 原 JSON Mode | 严格函数调用＋Pydantic＋原生消息配对 |
| --- | ---: | ---: |
| 完成任务 | 11/12 | 12/12 |
| 结构校验反馈 | 18 | 0 |
| 输入 Token | 221,912 | 364,273 |
| 平均耗时 | 14.79 秒 | 17.95 秒 |

**可说**：这批开发案例中结构稳定性改善，任务全部交付，输入和耗时同时增加。

**不要说**：Pydantic 单独使准确率提高，或者格式问题永久归零。这是协议、Schema、本地验证和历史配对的组合改造。

### 12.2 分批优化：输入明显降低，总耗时没有降低

固定 FunASR 提交的历史开发参考：

| 指标 | 旧版长历史 | 分批 v2.1 |
| --- | ---: | ---: |
| 模型调用 | 50 | 25 |
| 输入 Token | 11,344,663 | 192,774 |
| 审查阶段耗时 | 289.23 秒 | 294.67 秒 |
| 结果 | 达到次数上限，未完成 | 8/8 批交付 |
| 网页预览 | 30.14 秒 | 2.56 秒 |

输入相较历史记录下降约 98.30%，但范围、接口 Schema、日期和上下文策略存在变化。其中 28 个代码变更文件进入批次，另 16 个文档等只作上下文；不是严格单变量 A/B。

这张表是**复核接入前的发现引擎优化结果**，不能直接写成当前两阶段完整流程的同条件节省比例。没有新增一次全仓 v3 对照，就不能补造该数据。

**可说**：通过分批与受限检索控制重复历史，使这次受限代码范围得以交付，并显著减少历史运行的累计输入。

**不要说**：审查整体快了 98%、准确率提高 98%，或完整仓库语义已覆盖。

### 12.3 新增保留组：复核判别效果

8 个保留案例，两种证据条件使用同一候选、同样提示和 Schema、一次请求机会：

| 指标 | 局部锚点证据 | 调用与状态增强证据 |
| --- | ---: | ---: |
| 明确判别且正确 | 2 | 8 |
| 不确定 | 4 | 0 |
| 校验拒绝 | 2 | 0 |
| 判别覆盖率 | 2/8 | 8/8 |
| 已判别正确率 | 2/2 | 8/8 |
| 输入 Token | 11,043 | 13,570 |

增强证据在这组中多使用约 22.9% 输入，换来更高判别覆盖率。局部条件两次整体支持与必要判断不一致，被主机拒绝；失败保留，没有放宽规则重跑。

**可说**：在这 8 个刻意覆盖跨调用证据需求的合成案例中，补充证据改善了复核判别覆盖率。

**不要说**：代码审查准确率 100%，或没有任何输出错误。样本小、任务有构造偏差，局部条件也存在明确失败。

### 12.4 端到端结果与一个不能宣称的收益

8 个保留案例中，4 个预置缺陷各生成并保留 1 条与验收相符的报告，4 个正常改动没有告警。解释经过代码助手静态核对，尚未经项目开发者逐项确认。

由于正常案例在发现阶段就没有误报，**这次端到端评测没有证明复核把误报减少了多少**。给定错误候选被反驳，不能直接写成整个系统的误报率下降。

整个保留组套件共 38 次真实请求，已返回输入 69,599、输出 12,835 Token；这是多个案例与实验条件的合计，不是一个仓库任务。原命令因基线两次不合法结论非零退出，记录保留。

### 12.5 真实仓库例子：DKNet 和 FunASR

**DKNet 初次导入**：原循环 7 次调用，257,345 输入 Token，报告 3 项风险。两个边界问题获得受控原函数复现支持：所有候选图像不可读时的无界递归、空迭代器下训练辅助生成器无法恢复。第三项 checkpoint 配置风险只有部分支持。没有运行完整训练或真实数据集。

**FunASR 候选**：模型声称首包标志没更新，但另一个发送函数会更新它。第一版自动复核拿到了反证仍支持原复合主张；随后拆分必要判断、改进取证，最终返回待核实。保留原始失败，没有将其计为已确认缺陷，也没有证明它完全错误。

这两个例子可以体现你知道“代码证据、因果解释、受控复现、实际业务验收”是不同强度的支持。

### 12.6 自动测试应该怎样介绍

上一轮主项目记录为 **110 项 Python、9 项 Node 状态检查通过**，覆盖结构、工具、路径、证据、预算、Git 快照、SSE、页面状态和评测隔离等。

这些测试验证程序控制逻辑。真实模型实验另行记录；Node DOM 状态测试不能替代浏览器真实交互和视觉检查，测试数量也不等于模型效果分数。

## 13. 三个最值得准备的项目故事

### 故事 A：从“让模型输出 JSON”到真正可控的动作

**问题**：原 JSON Mode 在开发组出现 18 次结构反馈，多轮稳定性不足。

**分析**：不仅有文本格式问题，还有接口 Schema 子集差异、不同动作结构以及原生调用结果配对问题。单轮探针没法验证完整多轮协议。

**处理**：Pydantic 定义动作契约，生成远端兼容 Schema，采用严格函数调用，保留原生调用 ID，本地完整验证后执行。

**结果与代价**：相同 12 个开发案例由 11 个完成到 12 个完成，本次结构反馈为 0；耗时和输入上升。不能把稳定性、成本和语义质量混成一个指标。

### 故事 B：降低 Token 之后为什么还是超时

**问题**：FunASR 长历史累计输入超千万，50 次后仍没有完整交付。

**处理一**：分批独立上下文、片段检索，第一轮输入大幅降低，但拆成 14 批，串行请求约 10～14 秒，仍在五分钟耗尽时只交付 8 批。

**处理二**：紧凑 diff 减少重复字段，缩成 8 批，根据观测延迟为各批预留结束机会。

**结果与认识**：25 次调用完成 8/8 批，累计输入约 19.3 万，耗时仍约五分钟。瓶颈不只是输入量，还有请求数、生成量和接口延迟；没有承诺优化已使端到端更快。

### 故事 C：拿到反证，模型为什么还会误判

**问题**：FunASR 复核已经读到发送函数更新状态，但仍因为内部文本与展示文本不同而支持整个原候选。

**分析**：模型支持了某个局部事实，却没有否定已被反证破坏的故障链；证据存在与证据被正确使用是两回事。

**处理**：保留原候选，拆分故障机制、变更引入性和影响，校验整体判断的一致性；取回旧版调用和长函数尾部，并允许不确定。

**结果与认识**：该候选转为待核实；新保留组增强证据 8/8 匹配预期。但它不是自动语义证明，也不能据此宣称真实仓库误报已全部解决。

## 14. 面试高频追问与回答要点

以下用自己的话复述，不要逐字背。

### Q1：这个项目和把 diff 发给模型有什么区别？

模型可以按需调用只读工具获取跨文件上下文；宿主管理预算、结构和证据；候选还会补充前后版本证据进行复核。代价是多轮延迟和实现复杂度，因此保留只看 diff 的对照入口，不预设 Agent 一定更好。

### Q2：Agent 的“自主性”体现在哪？

模型决定是否读文件、搜什么、查哪个符号、何时提交候选；程序控制动作白名单、范围和结束条件。流程阶段由宿主编排，调查动作在范围内由模型选择。

### Q3：RAG 一定需要向量库吗？

不需要，核心是检索相关外部内容辅助生成。当前用 BM25 与 AST 取得代码原文；向量检索是否有用，需要在词法漏取证据的案例上比较。

### Q4：为什么不一次把整个仓库塞进去？

本地读取预算与模型上下文不是一回事。全量重复发送会增加输入成本、无关信息和历史累积；按变更和按需取证更容易控制，但要显式记录取证缺口及跨批遗漏风险。

### Q5：为什么 strict 了还要 Pydantic？

接口只支持部分 Schema，而且拒绝、截断、额外内容和本地长度范围仍需检查。接收端必须验证完整输入，再做路径与证据等业务校验。

### Q6：把温度设成 0 能解决输出问题吗？

不能。温度调整采样，不定义字段契约、不检查权限，也不证明代码语义。当前低温度只是配置之一，可靠性仍由协议、校验与评测组成。

### Q7：函数调用是不是模型直接执行 Python？

不是，接口返回指定函数的参数。宿主验证参数后执行自己的只读函数。复核传输函数只提交判断，不执行仓库代码。

### Q8：AST 能不能直接找出跨文件 bug？

AST 提供定义、位置和调用等结构，业务错误还依赖契约与行为。当前调用按名称和路径邻近性匹配，有别名、动态绑定和多态限制，不能当成完整语义分析器。

### Q9：怎么保证模型引用没有编造？

核对快照、版本、行号和完整原文，再要求引用位于该次模型已展示的范围。这样提高引用可追溯性；解释是否成立仍需复核或独立验收。

### Q10：复核不就是同一模型再问一次吗？

不仅换上下文，还增加调用与旧版证据，明确寻找反证，把机制、引入性、影响拆开判断，并检查一致性。但同模型可能共享盲点，所以最终仍允许待核实，并用独立验收检查效果。

### Q11：为什么不确定不能直接扔掉？

扔掉会把预算不足、工具失败或证据不全伪装成没有问题。保留候选和限制，才能让使用者判断后续核查事项，也方便统计真正的判别覆盖率。

### Q12：调用次数变少为什么没更快？

总耗时包括请求等待、输入处理、输出生成和本地处理。新的每轮承担更多调查或详细结论；当前还串行等待完整 JSON。历史记录只能确认总时长未下降，没有逐项数据就不能把原因全部归给结构化输出或供应商。

### Q13：资源缺失靠一句提示能解决吗？

提示只提供背景。实际还有读取前过滤、快照内访问、不可用记录缓存、重复保护和总预算；没有提供任意路径读图或下载资源的能力。

### Q14：数据不在，为什么还能审查 data.py？

审查的是数据处理代码，不是验证数据内容。可以发现有证据的空值、索引或失败处理风险，但不能判断真实数据分布、训练效果或模型精度。

### Q15：给出一组正常代码没有告警，能算低误报吗？

只能说明这组案例的表现，还要报告样本量、正常案例类型和未完成情况。当前保留组只有 4 个正常改动，不足以支撑通用误报率承诺。

### Q16：8/8 是不是 100% 准确率？

这是 8 个特定保留合成案例上的匹配结果。复核与端到端指标不同，数据构造和样本量有限，还需要新案例、真实仓库验收与重复试验。

### Q17：为什么评测要冻结输入构造器？

即使案例没改，构造器也可能把标签或更多信息放进模型。冻结它与验收程序，有助于检查不同运行是否保持同一实验定义；这不等于完全消除偏差。

### Q18：项目最主要的技术难点是什么？

优先讲三个：多轮工具协议与结构稳定性；有限上下文和时间下的证据获取与交付；区分引用真实、模型支持和缺陷被验收。每个难点接一个真实失败与改进结果。

### Q19：为什么没用数据库和队列？

当前范围是单机演示与评测，内存任务和线程足够验证闭环。代价是无法跨重启恢复、排队多用户任务或分布式执行；这些是下一阶段工程化问题，未实现就不写成已有能力。

### Q20：如果再给你时间，你优先改什么？

先把请求等待、输出生成、本地取证和复核耗时拆清，再减少重复内容或比较有限并行；同时用固定条件和新保留案例检查质量。之后再做任务持久化和 PR 集成。当前这些只是规划。

## 15. 可以直接练习的项目介绍

### 15.1 约 30 秒版本

> 我做了一个本地代码审查 Agent，面向 Python 的 Git 变更。它把变更分批，模型通过搜索、读文件和 AST 定位按需获取证据，再对候选结合前后版本与调用关系进行复核。主要工作是严格函数调用加 Pydantic、上下文和预算控制、证据可追溯，以及独立评测。当前是本地静态审查 Demo，结果区分模型支持、反证和待核实。

### 15.2 约 2～3 分钟版本

> 我希望解决一次性把 diff 给模型时上下文不足、长对话成本高，以及报告难以核实的问题，所以做了一个本地代码审查工作台。
>
> 输入是两个固定 Git 提交，也支持首次导入。程序过滤数据和权重，按变更生成有限批次，每批独立历史。模型可以按行读代码、做 BM25 片段检索和 AST 定义定位。动作采用 DeepSeek 严格函数调用，本地再用 Pydantic 和白名单校验。
>
> 第一个重点是成本与交付。旧版持续发送完整历史，FunASR 历史运行累计输入超过一千万，达到 50 次仍没完成。改为紧凑分批和按需检索后，一次固定提交的受限审查使用约 19.3 万输入，8 批交付；但两次范围和接口存在变化，耗时仍约五分钟，所以我没有把它描述为严格 A/B 提速。
>
> 第二个重点是结果可靠性。我记录模型实际看到的代码行，要求报告引用真实且已展示的原文，再为候选补充调用方、被调用方、装饰器和旧版证据。复核分别判断故障机制、变更引入性和影响，允许不确定，不把结构合法当成缺陷成立。
>
> 评测方面新增 12 个合成案例，4 个开发、8 个冻结保留，答案与验收不进入模型。保留组增强证据条件 8/8 匹配预期；端到端报告了 4 个预置缺陷，4 个正常改动没有告警。样本很小，我保留失败与未知记录，不把它当通用准确率。当前主要限制是静态匹配、单任务和内存状态，生产化还没有完成。

## 16. 按这个顺序学，知道何时算掌握

### 16.1 第一层：必须讲清，不需要背公式

| 内容 | 自测题 |
| --- | --- |
| 项目输入输出 | 用户输入什么？为什么必须先预览固定提交？ |
| Agent 循环 | 模型决定了什么？程序执行了什么？由谁结束？ |
| 结构与语义 | JSON 合法为什么仍会误报？ |
| Token | 为什么 65 KB 的仓库多轮累计输入可能很大？ |
| RAG | 检索发生在哪一步？为什么没用向量库？ |
| 报告状态 | 零问题、未完成、待核实分别怎么解释？ |
| 项目边界 | 哪些能力是已实现，哪些只是下一阶段？ |

能不看资料连续讲完 3 分钟流程，并回答这些问题，才进入下一层。

### 16.2 第二层：解释机制和取舍

重点学严格函数调用与调用 ID 配对、BM25 的词频与长度归一化、AST 局限、证据台账、三项复核判断、共享预算和 SSE 恢复。

每个机制按四句话练习：**遇到什么问题 → 怎么实现 → 带来什么代价 → 用什么证据验证**。

例如：“分批”不是只背“减少 Token”，还要能说独立历史为什么减少重复、跨批信息为什么可能丢失、未完成怎么展示，以及历史实验为什么不是严格 A/B。

### 16.3 第三层：能应对研究生秋招深入追问

你应该能主动讨论：

- 如何区分检索漏取关键证据、模型推理错误、结构错误和执行控制失败。
- 为什么要让系统允许不确定，又如何避免靠大量弃判得到漂亮正确率。
- 给定候选评测为什么无法证明自主发现能力。
- 正常案例没有原始误报时，为什么不能声称复核减少了端到端误报。
- 同一模型独立上下文为什么仍存在相关错误。
- 如何设计同提交、同范围、同预算的速度与质量对比，如何处理服务端模型别名变化。
- 当前不可用资源缓存和重复调用去重解决了什么，为什么不是通用的推理收敛保证。

### 16.4 不改代码也能做的学习练习

1. 在纸上画出第 3 节流程，在每个箭头旁标注“谁执行、输入是什么、失败怎么办”。
2. 用折扣、空值、正常重构各举一例，说明模型为什么需要或不需要补充上下文。
3. 口述 FunASR 两次失败：分批后仍超时；得到反证仍误判。说清改进后的收益与未解决问题。
4. 自己计算第 12 节两种复核条件的覆盖率和正确率，解释它们为何不能只报 100%。
5. 录一段 3 分钟介绍，删掉所有不能解释的框架词，换成具体机制。

| Structured Outputs | 输出受结构契约约束 | 本项目落地为严格函数调用，不是任意厂商都保证相同能力 |
| Schema | 字段类型和结构约定 | 从 Pydantic 生成远端兼容子集 |
| Discriminated Union | 用一个字段判断数据属于哪种结构 | action 区分工具与 final |
| RAG | 检索外部信息后辅助生成 | 本地代码词法与结构检索 |
| BM25 | 按词频、稀有度和长度排序 | 片段检索，外加字面匹配加分 |
| AST | 源码的语法结构树 | 定义定位、调用和装饰器线索 |
| Evidence Ledger | 记录模型实际看过的代码行 | 发现阶段引用可见性校验 |
| Counterevidence | 能否定原候选关键判断的证据 | 复核必须主动寻找 |
| Holdout | 开发时不据其结果调参的保留数据 | 新增 8 例，已完成首次观察 |
| Oracle | 指定契约的独立验收依据 | 只用于可信合成微型案例 |
| Ablation／对照 | 改变一部分信息或机制观察差异 | 局部证据与增强证据对照 |
| Abstention／弃判 | 证据不足时不强制支持或反驳 | uncertain，与失败原因分别记录 |
| SSE | 服务端单向推送事件 | 执行轨迹，不等于模型文本流式输出 |
| Deadline | 统一的截止时间 | 发现与复核共享总时限 |
| Telemetry | 用于分析运行情况的记录 | 逐轮用量、耗时、请求大小等；不是完整生产监控平台 |
| Prompt Injection | 外部内容试图改变模型指令 | 源码视为数据，宿主权限边界另行约束 |
