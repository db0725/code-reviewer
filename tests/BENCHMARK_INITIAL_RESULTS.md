# DKNet 第一轮测试：结果与结论

> 独立基准仓库的结果说明副本，便于本仓库直接阅读；未包含原始实验输出或基准源码。原文件 SHA-256：`e29f6c6c8ee1719e3fb8b6f221dbf9b4e3412c4067e5282754694cc499f6ccb1`。历史实验路径仍以原基准目录为准。

已完成 20 个固定改动的两组真实 DeepSeek 测试，共 40 次审查任务。源代码固定为 DKNet 提交 `ec79fbe23002412586589f04267a26985338eeb0`，没有修改上游仓库。本轮没有根据保留组结果调整模型或提示词，也没有将失败任务重跑后替换掉。

## 这次究竟测了什么

测试目录包含原始代码副本和 20 份单独补丁：10 份让独立函数验收测试失败，10 份保持测试通过。先确认原版本通过全部验收，再启动模型审查。

范围只包括路径处理、CSV 校验、坐标解析；没有测试完整训练、张量热图计算或医学模型效果。10 个“有缺陷”标签首先表示预设函数契约被破坏，业务影响仍需要检查真实调用路径，不能将全部标签直接视为已确认的业务 Bug。

## 哪些地方体现了查阅代码的价值

- **DK009：无标注 CSV 的 Path 列检查被删除。** Agent 查阅 README 和实际调用后，指出默认模式会触发 KeyError，关闭文件检查时又会静默放过缺列。只看 diff 的基线没有报告。该结论符合完整代码及验收场景。
- **DK017：嵌套坐标的 x/y 被反转。** Agent 找到数据加载代码和另一处解析函数，指出关键点与热图目标会错位。只看 diff 的基线没有报告。对非对称嵌套坐标，独立验收能够复现差异。

## 暴露的问题与标签边界

- **DK001：Agent 没有完成。** 模型连续返回单个 JSON 对象之外的内容，宿主三次拒绝后停止；基线找出了相对路径处理问题。失败记录保留，没有当作“没有 Bug”。
- **DK003：预设标签值得修正定义。** 独立测试确实发现校验脚本的坐标返回顺序变化，但 Agent 查阅调用方后指出，现有 CSV 校验仅检查能否解析，并不消费返回的坐标。因此不能只凭函数返回值不同，就认定现有命令行校验功能被破坏。下一版应归为契约变化案例，或移到实际消费坐标的路径验证业务影响；本轮冻结集不追改。
- **DK011：坐标小数精度丢失未被报告。** Agent 以“误差不到一个像素”为由认为影响有限。数值截断是确定的行为变化，但是否符合业务容忍度没有外部约定；不能仅凭模型自述认定可接受，也不能用当前小样本推断医学性能。下一版需要明确浮点坐标保真要求。
- **DK013：问题位置正确，路径解释有错误。** 两组都指出拼接参数反转，但给出的绝对根目录拼接示例不准确：`os.path.join(relative, absolute_root)` 会保留后面的绝对根目录、丢弃相对文件名，并不是把两段直接连接。实际缺陷成立，说明报告解释仍需复核。

这几项说明“能运行”“找到正确行”“解释正确”应分别评估，不适合把位置统计直接写成模型准确率。

## 下一步应该优化什么

1. **先改善协议稳定性。** Agent 组共有 27 条输出校验反馈，主要是单次输出多个 JSON 动作或附加内容。应继续保持严格执行边界，改进动作输出方式，不能简单截取第一段并忽略其余内容。
2. **压缩查阅上下文。** Agent 输入 token 约为基线的 30.41 倍。这批例子中大量整文件内容被反复带回模型；可以改为按函数或行段读取、去重和限制上下文预算，再衡量收益。没有按 token 比例估算实际费用。
3. **明确业务契约，增加新的独立样本。** 对 DK003、DK011 这类案例补充可观察的业务结果要求，再加入自然发生的修复及更复杂跨文件变更。优化后使用新的保留集，保留本轮结果作为初始基线。
